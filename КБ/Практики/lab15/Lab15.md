# Практическая работа № 15. Учебное реагирование на инцидент

**Дисциплина:** Операционные системы. **Специальность:** 10.05.01 «Компьютерная безопасность», университет, 3-й курс. **Продолжительность:** 90 минут; снимки и проверка стенда выполняются заранее. **Варианты:** 27, номер соответствует номеру студента по списку в журнале.

Тема взята из раздела 4.2 РПД: получение сценарной карточки (серия неуспешных входов и изменение тестового файла), сохранение журналов, локализация источника, восстановление конфигурации и подготовка краткого отчёта. Работа опирается на лекции 13 «Журналирование, аудит и контроль целостности» и 16 «Реагирование, восстановление и современные тенденции» и продолжает стенд из ПР1, работу с журналами из ПР10, усиление SSH из ПР12 и контроль целостности из ПР13. Здесь эти навыки собираются в один цикл реагирования.

**Вариант для предоставленного «Орла» 2.12.22:** Astra Linux Common Edition «Орёл» 2.12.22 на базе Debian 9: ядро 4.15, Python 3.5, sshd из OpenSSH выпуска, журналирование через systemd-journald и rsyslog в `/var/log/auth.log`. Инцидент готовит скрипт: он подкладывает на учебную Astra журналы с серией неуспешных входов по SSH (`/var/lib/pr15/incident`), изменённые файлы учебной службы `pr15-agent` в `/srv/pr15` и доверенный эталон этих файлов, снятый до инцидента (`/var/lib/pr15/baseline`). Так разбор не зависит от настоящего sshd и воспроизводится одинаково; как выглядят те же события в живой системе, показано в теории и в необязательном шаге с Kali. На Kali нужен только клиент OpenSSH и Python 3.

**Граница результата:** работа ведётся на собственной Astra с собственной Kali. Все изменения затрагивают только учебные объекты в `/srv/pr15` и `/var/lib/pr15`. Журналы инцидента и эталон доступны только для чтения; восстановление берёт файлы из эталона и не трогает `/var/log` и системные конфигурации. Необязательный шаг с Kali делает ограниченную, заведомо неуспешную серию попыток входа (пароли не подбираются). Содержание инцидента (какой источник, какой аккаунт, какие файлы) до команды reveal не раскрывается; файл `/var/lib/pr15/state.json` до reveal не открывают. Пароли и закрытые ключи в отчёт не включаются.

## 1. Цель и результаты

Цель — пройти цикл реагирования на учебный инцидент: сохранить журналы и состояние файлов с фиксацией контрольных сумм, по журналам локализовать источник серии неуспешных входов и установить, удался ли вход, отличить вредоносные изменения файлов от санкционированных и штатных, восстановить конфигурацию из доверенного эталона и подготовить краткий отчёт.

Задачи:
- сохранить журналы инцидента и снимок состояния файлов службы в дело с контрольными суммами и защитой от записи (chain of custody);
- по журналу `auth.log` определить источники попыток входа, отличить серию перебора от разового промаха легитимного пользователя, подсчитать попытки, найти первый и последний неуспех;
- установить целевой аккаунт и по строке `Accepted` определить, удался ли вход и когда; сопоставить время изменения файлов со временем сессии;
- классифицировать каждое изменение файла: вредоносное (восстановить), санкционированное по заявке (не трогать), штатное (рост журнала);
- восстановить вредоносно изменённые файлы из доверенного эталона и подтвердить восстановление сверкой с эталоном;
- подготовить краткий отчёт по инциденту (идентификация, источник, хронология, последствия, восстановление, выводы);
- выполнить самопроверку, итоговую проверку состояния и удалить учебные объекты.

Результат — сохранённое дело с манифестом SHA256, таблица источников и хронология, заполненные `findings.csv` и `files.csv`, протоколы восстановления и сверки с эталоном, краткий отчёт `report.md`, протокол самопроверки (reveal), итоговая проверка (check) и подтверждение удаления. Не приписывайте источнику то, что не следует из журналов, и не восстанавливайте санкционированное изменение: одно из изменений файлов разрешено заявкой.

## 3. Теория: жизненный цикл инцидента и журналы входа

**Жизненный цикл реагирования.** Реагирование на компьютерный инцидент принято делить на фазы: подготовка; обнаружение и анализ; сдерживание, устранение и восстановление; действия после инцидента (выводы). В этой работе подготовка уже выполнена (есть стенд, эталон и журналы), а студент проходит остальные фазы: обнаруживает и анализирует событие по журналам, локализует источник, устраняет последствия восстановлением из эталона и фиксирует выводы в отчёте. На каждом шаге сохраняется доказательная база.

**Сохранение доказательств.** Первое действие — сохранить журналы и состояние системы, пока они не затёрты. Копии складывают в отдельное «дело», вычисляют для каждого файла контрольную сумму и защищают от записи; фиксируют время сбора и исполнителя. Это и есть chain of custody: позже по контрольным суммам видно, что доказательства не менялись. Восстановление выполняют только после сохранения — иначе будут потеряны следы.

**Журналы входа по SSH.** sshd записывает события аутентификации. В Debian/Astra они идут в `/var/log/auth.log` (через rsyslog) и в журнал systemd (journald). Характерные строки:

| Строка | Что означает |
|---|---|
| `Failed password for USER from IP port N ssh2` | неуспешный ввод пароля для существующего пользователя |
| `Invalid user USER from IP port N` и `Failed password for invalid user USER …` | попытка входа под несуществующим пользователем |
| `Accepted password for USER from IP port N ssh2` | успешный вход по паролю |
| `Accepted publickey for USER …` | успешный вход по ключу |
| `pam_unix(sshd:session): session opened/closed for user USER` | открытие и закрытие сессии |

Те же данные доступны иначе: `journalctl -u ssh` (или `-u sshd`) — журнал службы; `last` читает `/var/log/wtmp` (успешные входы), `lastb` — `/var/log/btmp` (неуспешные, нужен root). Форматы строк в auth.log и journald совпадают по сути; в работе основной источник — `auth.log`, а `journal.txt` в деле даёт перекрёстную сверку.

**Локализация источника.** Источник перебора выделяют по частоте: на него приходится много строк `Failed password`/`Invalid user` за короткое время. Разовый `Failed password` с другого адреса — это, как правило, промах легитимного пользователя (опечатка), а не атака; его отличает малое число попыток и часто последующий `Accepted` для того же пользователя. Поэтому источники сортируют по числу неуспехов:

```
grep -E 'Failed password|Invalid user' auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn
```

(поле с адресом зависит от формата строки; удобнее пользоваться сводкой команды `timeline`). Серия перебора задаёт окно: первый и последний неуспех. Если в этом окне или сразу после него есть `Accepted` **с того же адреса** для подбираемого аккаунта — вход удался, и начинается разбор того, что сделал нарушитель.

**Корреляция: связаны ли события.** Сценарная карточка называет два факта: серию неуспешных входов и изменение файлов. Их нельзя автоматически считать одним событием — связь нужно доказать. Главный приём — сопоставление времени. У изменённого файла есть время изменения содержимого (mtime); его читает `stat`. Если mtime попадает в интервал сессии, открытой успешным входом нарушителя, изменение приписывают этой сессии. Если mtime относится к другому времени и объясняется заявкой на плановое изменение (с консоли, под учётной записью администратора) — это санкционированное изменение, не связанное с перебором. Рост служебного журнала — штатная активность. Так одни и те же «изменения» получают разные вердикты.

**Разрешённое, вредоносное и штатное.** Как и в контроле целостности (ПР13), отличие файла от эталона само по себе не доказывает атаку. Каждое изменение сопоставляют с известной заявкой на плановое обслуживание (её текст выдаётся вместе с инцидентом). Совпадающее с заявкой — санкционированное, восстанавливать его нельзя: это затрёт разрешённую работу. Не предусмотренное заявкой и связанное с сессией нарушителя — вредоносное: его восстанавливают и разбирают. Объяснимое штатной работой (рост журнала) — нормальная активность.

**Восстановление из доверенного эталона.** Источник восстановления должен быть доверенным и снятым до инцидента, иначе можно «восстановить» уже испорченный файл. В работе это эталон `/var/lib/pr15/baseline`, доступный только для чтения. Восстановленный файл совпадает с эталоном по содержимому и правам. Нарушитель с правами root мог бы и подменить файл, и подделать его mtime, поэтому для надёжного сравнения используют хеш, а не только время. Неожиданный новый файл не удаляют сразу: записывают его хеш и перемещают в карантин для разбора.

**Что имитирует учебная среда.** Журналы инцидента подложены заранее и неизменны, поэтому разбор детерминирован и одинаков у всех. На живой системе те же строки писал бы работающий sshd в реальном времени, журнал рос бы и ротировался, а время зависело бы от синхронизации часов (ПР10). Это ограничение отмечают в отчёте. Необязательный шаг 2 показывает настоящие записи: Kali делает ограниченную серию неуспешных входов, и они появляются в живом журнале Astra.

**Astra Special Edition.** В Astra Linux SE есть собственные средства регистрации событий безопасности и реагирования в составе КСЗ (лекция 10), а подключение к ГосСОПКА регламентирует взаимодействие с НКЦКИ. Принципы — сохранить доказательства, локализовать, восстановить, зафиксировать выводы — те же, что в этой работе.

## 4. Индивидуальное задание

Каждый вариант получает свой стенд (адреса Astra и Kali, адрес внутреннего узла-шума), номер инцидента `INC-15-NN` и номер заявки на санкционированное изменение `CHG-15-NN`. Содержание самого инцидента (источник, целевой аккаунт, какие файлы испорчены, удался ли вход) выбирается при инициализации случайно и не публикуется: его устанавливают по журналам.

## 5. Ход выполнения

### Шаг 1. Карточка инцидента и сохранение журналов — 15 минут

Astra, обычная учебная запись:

```bash
mkdir -p "$HOME/pr15" && cd "$HOME/pr15" || exit
V=1; NN=$(printf %02d "$V"); W="$HOME/pr15"; T="$W/kit/tools/pr15.py"; P="$W/kit/tools/pr15_probe.py"
sudo python3 "$T" init --work "$W" --variant "$V"
python3 "$T" info --work "$W" --field chg_text | tee evidence/ticket.txt
KALI_IP=$(python3 "$T" info --work "$W" --field kali)
ip -4 address show | tee evidence/addresses.txt
```

Замените 1 своим вариантом; держите терминал открытым, переменные действуют в нём. Прочитайте карточку инцидента, которую напечатал `init`, и текст заявки CHG. Сразу сохраните журналы и состояние файлов в дело:

```bash
sudo python3 "$T" preserve
```

Ожидание: `init` сообщает номер инцидента, адрес Astra, расположение журналов и эталона и текст санкционированного изменения. `preserve` копирует `auth.log`, `journal.txt`, манифест эталона и снимок состояния файлов (`file-state.json`) в `/var/lib/pr15/case` и в `evidence/case`, делает их только для чтения, вычисляет для каждого SHA256 и печатает `CASE-MANIFEST SHA256`. Запишите это значение в отчёт: дальше оно подтверждает неизменность доказательств. Восстановление выполняется только после этого шага.

### Шаг 2. Необязательно: реальная серия входов с Kali — 10 минут

Если на стенде поднят sshd и занятие включает этот шаг, покажите, как инцидент выглядит в живом журнале. Kali, обычная запись:

```bash
cd "$HOME/pr15" || exit
V=1; ASTRA_IP="10.50.$V.10"; P=kit/tools/pr15_probe.py
python3 "$P" knock --host "$ASTRA_IP" --user admin --attempts 8
```

Серия ограничена (не более 15 попыток), пароли не подбираются: используется несуществующий ключ и пользователь, каждая попытка завершается отказом. Затем на Astra захватите живой журнал:

```bash
sudo python3 "$T" capture
cat evidence/live-auth.txt
```

Ожидание: на Kali восемь строк `rc=255 Permission denied`; в `evidence/live-auth.txt` — строки `Failed password`/`Invalid user` с адреса Kali из настоящего журнала Astra. Сравните их формат со строками в `/var/lib/pr15/incident/auth.log`. Если sshd на стенде не настроен или шаг пропускается, разбор идёт по журналам из шага 1 — на оценку это не влияет.

### Шаг 3. Анализ: источник и хронология — 15 минут

Astra. Журналы инцидента читаются обычными средствами (они доступны на чтение):

```bash
AUTH=/var/lib/pr15/incident/auth.log
grep -E 'Failed password|Invalid user' "$AUTH" | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn | tee evidence/by-source.txt
grep 'Accepted' "$AUTH" | tee evidence/accepted.txt
```

Затем постройте сводку скриптом — он считает попытки по источникам, показывает первый и последний неуспех, строки `Accepted` и отличия файлов службы от эталона с их mtime:

```bash
python3 "$T" timeline --work "$W"
```

Ожидание: один адрес даёт много неуспехов (источник перебора), другой — один-два (разовый промах, обычно с последующим `Accepted` для того же пользователя). В разделе отличий видно, какие файлы изменены и когда. Сопоставьте mtime изменённых файлов со временем строки `Accepted` источника и со временем заявки CHG из шага 1. Определите: адрес источника, целевой аккаунт (валидный, который перебирали; несуществующие имена из строк `Invalid user` — это сканирование, а не целевой аккаунт), число попыток, первый и последний неуспех, удался ли вход и когда.

### Шаг 4. Локализация и классификация — 15 минут

Astra. Заполните `findings.csv` по таблице 5. Времена копируйте строками точно из журнала:

```bash
cat > findings.csv <<'EOF'

```

Заполните `files.csv` по таблице 6 — по строке на каждый изменённый объект из сводки `timeline`. Санкционированное изменение (файл из заявки CHG) помечайте `authorized,keep`, вредоносные — `malicious,restore`, рост журнала — `normal,keep`:

```bash
cat > files.csv <<'EOF'

/srv/pr15/conf/agent.conf,malicious,restore,изменён в сессии входа с 10.50.1.20 в SUCCESS_TIME
```

Ожидание: `localize` проверяет только формат обоих файлов и печатает ваши значения. Содержание (правильность) проверяется позже командой reveal; сверьте свои выводы с журналом ещё раз перед восстановлением.

### Шаг 5. Восстановление конфигурации — 15 минут

Astra. Восстановите вредоносно изменённые файлы из доверенного эталона. Команда действует строго по `files.csv`: объекты с `action=restore` берутся из эталона, с `quarantine` — переносятся в карантин, с `keep` — остаются:

```bash
sudo python3 "$T" restore
```

Ожидание: для файлов с `restore` печатается «восстановлен из эталона», затем сверка: вредоносные файлы теперь совпадают с эталоном, санкционированный — отличается (он сохранён). Если санкционированный файл показан как совпавший с эталоном — вы ошибочно восстановили разрешённое изменение; исправьте `files.csv` и запустите снова (эталон не изменяется). В отчёте укажите, какие файлы и почему восстановлены, а какие сохранены.

### Шаг 6. Краткий отчёт — 10 минут

Astra. Напишите `report.md` — краткий отчёт по инциденту. Обязательные разделы (заголовки): «Идентификация», «Источник», «Хронология», «Последствия», «Восстановление», «Выводы». Укажите номер инцидента и адрес источника. Проверьте отчёт:

```bash
python3 "$T" report --work "$W"
```

Ожидание: все разделы присутствуют, указаны `INC-15-NN` и адрес источника, объём 40–1200 слов — «Отчёт принят». Отчёт краткий: по одному-два абзаца на раздел. Пароли и значения секретов в отчёт не включайте.

### Шаг 7. Самопроверка, итоговая проверка и удаление — 10 минут

Astra. Раскройте истину инцидента и сверьте её со своими выводами, затем выполните итоговую проверку:

```bash
sudo python3 "$T" reveal
sudo python3 "$T" check
```

Ожидание: `reveal` сравнивает `findings.csv` и `files.csv` с истиной и печатает счёт совпадений; расхождения разберите в отчёте. `check` — все строки OK и `passed: True`: журналы сохранены и целы (манифест совпадает), источник/аккаунт/число попыток/факт входа определены верно, времена соответствуют журналу, классификация файлов верна, вредоносные файлы восстановлены, а санкционированный сохранён, отчёт принят, самопроверка выполнена; строка живого захвата — OK и при пропуске шага 2. Удалите учебные объекты и зафиксируйте суммы:

```bash
sudo python3 "$T" cleanup --yes
sha256sum evidence/* 2>/dev/null > SHA256SUMS.txt
sha256sum session.json findings.csv files.csv report.md >> SHA256SUMS.txt
sha256sum -c SHA256SUMS.txt
```

Ожидание: `cleanup` удаляет `/srv/pr15` и `/var/lib/pr15` и печатает `"clean": true`. Дело `evidence/case` и заполненные файлы остаются в рабочем каталоге как доказательства.

2. [sshd(8), Debian 9](https://manpages.debian.org/stretch/openssh-server/sshd.8.en.html) и [auth.log / PAM](https://manpages.debian.org/stretch/libpam-runtime/pam.8.en.html) — строки аутентификации.
3. [journalctl(1), Debian 9](https://manpages.debian.org/stretch/systemd/journalctl.1.en.html) — журнал systemd, фильтр по службе ssh.
4. [last(1), lastb(1), Debian 9](https://manpages.debian.org/stretch/util-linux/last.1.en.html) — `/var/log/wtmp` и `/var/log/btmp`.
5. [NIST SP 800-61 Rev. 3 (2025). Incident Response Recommendations and Considerations](https://csrc.nist.gov/pubs/sp/800/61/r3/final) — жизненный цикл реагирования; заменяет Rev. 2 (2012).
6. [NIST SP 800-92 (2006). Guide to Computer Security Log Management](https://csrc.nist.gov/pubs/sp/800/92/final) — сбор, хранение и анализ журналов.
7. [ФСТЭК России. Меры защиты информации в ГИС, 11.02.2014](https://legalacts.ru/doc/metodicheskii-dokument-mery-zashchity-informatsii-v-gosudarstvennykh/) — группы мер РСБ «Регистрация событий безопасности» и ИНЦ «Реагирование на компьютерные инциденты».
8. [НКЦКИ / ГосСОПКА](https://www.gov.cert.ru/) — взаимодействие при компьютерных инцидентах.
