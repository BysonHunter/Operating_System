# Практическая работа № 14. Анализ изоляции виртуальной машины и контейнера

**Дисциплина:** Операционные системы. **Специальность:** 10.05.01 «Компьютерная безопасность», университет, 3-й курс. **Продолжительность:** 90 минут; проверка ядра и снимки выполняются заранее. **Варианты:** 27, номер соответствует номеру студента по списку в журнале.

Тема взята из раздела 4.2 РПД: сравнение границ изоляции, сетей, файловых систем и привилегий; проверка запуска контейнера без привилегий и с ограничениями ресурсов. Работа опирается на тему 15 «Виртуализация, контейнеры и изоляция» и на практические работы курса: в ПР1 создан стенд из двух ВМ во внутренней сети и снимки, в ПР2 у процессов определялась cgroup, в ПР3 изучались capabilities. Здесь те же механизмы сравниваются на трёх уровнях: отдельная виртуальная машина (Kali), контейнер со слабой изоляцией и контейнер без привилегий на Astra.

**Вариант для предоставленного «Орла» 2.12.22:** Astra Linux Common Edition «Орёл» 2.12.22 на базе Debian 9: ядро 4.15 (в ПР8 зафиксировано 4.15.3-1), Python 3.5, util-linux 2.29 (`lsns`, `nsenter`, `unshare`), systemd 232. Стенд изолирован, поэтому Docker и образы из интернета не используются. Контейнер запускает учебная среда выполнения `pr14.py` на тех же механизмах ядра, что runc, Docker и LXC: пространства имён, `pivot_root`, отображение UID, capabilities, `no_new_privs` и cgroups. Образ — каталог `/var/lib/pr14/rootfs` с собственным `/etc`; системные каталоги (`/usr`, `/bin`, `/lib` и др.) подключаются из хоста только для чтения, тогда как в образах OCI они свои. Скрипт сам определяет cgroup v1 или v2; для ядра 4.15 с systemd 232 ожидается v1 с иерархиями `memory`, `pids` и `cpu`. На Kali нужны только Python 3 и SSH-клиент.

**Граница результата:** работа выполняется на собственной Astra с собственной Kali. Контейнеры запускаются только командой `pr14.py run`. Корень контейнера — образ ПР14, источники томов — только каталоги внутри `/srv/pr14`, ограничивающий профиль сверяется скриптом с вариантом. Нагрузочные тесты ограничены: память не более 256 МБ, не более 128 процессов, CPU — 3 секунды. Проверки привилегий безвредны и выполняются внутри контейнера: raw-сокет сразу закрывается, tmpfs отмонтируется, MTU интерфейса loopback записывается прежним. Kali Astra не сканирует, а только принимает подключения. Файл `/srv/pr14/host/secret.txt` — учебная строка: в отчёт вносится факт чтения и совпадение хеша, но не значение. Пароли в отчёт не включаются.

## 1. Цель и результаты

Цель — экспериментально сравнить границу изоляции виртуальной машины и контейнера, установить, какие ресурсы ядра контейнер разделяет с хостом, построить профиль контейнера без привилегий с ограничениями ресурсов и подтвердить его свойства измерениями изнутри и наблюдением с хоста.

Задачи:
- зафиксировать параметры ВМ в гипервизоре, снять отпечаток контекста на Astra и на Kali и доказать, что у ВМ собственное ядро;
- запустить контейнер со слабой изоляцией и показать, что его root — root хоста: чтение секрета хоста, запись в каталог хоста, общая сеть и общий список процессов;
- составить профиль контейнера без привилегий по варианту и проверить его скриптом, в том числе на заведомо ошибочном профиле;
- запустить контейнер без привилегий и подтвердить: шесть собственных пространств имён, отображение root на uid варианта, ровно разрешённые capabilities, `no_new_privs`, корень и `/hostdata` только для чтения, отсутствие сети наружу;
- проверить ограничения памяти, числа процессов и CPU нагрузочными тестами и счётчиками cgroup, сравнить с контейнером без ограничений;
- наблюдать оба контейнера со стороны хоста: `ps`, `lsns`, `/proc/PID`, файлы cgroup;
- свести измерения в матрицу, оценить каждое свойство для ВМ и двух контейнеров, сверить оценку с измерениями, выполнить итоговую проверку и удалить учебные объекты.

Результат — отпечатки четырёх контекстов (Astra, Kali, контейнер shared, контейнер restricted), профиль и протокол его проверки, результаты сетевых и нагрузочных тестов, протоколы наблюдения с хоста, матрица изоляции, таблица `isolation.csv` с самопроверкой, итоговая проверка и подтверждение удаления. Не переносите на контейнер свойства ВМ: у контейнера ядро общее с хостом, и это видно в каждом измерении.

### 2.1. Проверка ядра и комплекта

На Astra, обычная учебная запись:

```bash
cat /etc/os-release
cat /etc/astra_version 2>/dev/null
uname -r
python3 --version
python3 -c 'import ctypes; print("ctypes OK")'
ls -l /proc/self/ns
cat /proc/sys/user/max_user_namespaces
cat /proc/sys/kernel/unprivileged_userns_clone 2>/dev/null
grep -E '^(memory|pids|cpu)\s' /proc/cgroups
grep cgroup /proc/mounts
for c in lsns nsenter ps pgrep sudo; do command -v "$c" || printf 'ОТСУТСТВУЕТ: %s\n' "$c"; done
systemctl is-active ssh
cd "$HOME/pr14/kit" && sha256sum -c SHA256SUMS.txt | grep -v ': OK$'; cd "$HOME/pr14" || exit
```

На Kali:

```bash
python3 --version
for c in scp ssh-keygen; do command -v "$c" || printf 'ОТСУТСТВУЕТ: %s\n' "$c"; done
cd "$HOME/pr14/kit" && sha256sum -c SHA256SUMS.txt | grep -v ': OK$'; cd "$HOME/pr14" || exit
```

Ожидание: в `/proc/self/ns` есть `cgroup`, `ipc`, `mnt`, `net`, `pid`, `user`, `uts`; `max_user_namespaces` больше 0; у `memory`, `pids`, `cpu` в последнем столбце `/proc/cgroups` стоит 1; проверка сумм не выводит строк. Запишите значение `unprivileged_userns_clone`, если файл есть: в ядрах Debian до 5.10 по умолчанию 0, то есть обычный пользователь не может создать пространство имён пользователей. Работе это не мешает: контейнер создаёт root через sudo, а root контейнера отображается на непривилегированный uid хоста.

### 2.2. Если чего-то не хватает

Пакеты устанавливать не нужно. Docker, LXC и сторонние репозитории не подключайте. Если у `memory` в `/proc/cgroups` стоит 0, ядро загружено с выключенным контроллером памяти: параметр загрузки `cgroup_enable=memory` добавляет преподаватель. Если `user.max_user_namespaces` равен 0, временно разрешите создание (`sudo sysctl -w user.max_user_namespaces=1000`) только с разрешения преподавателя, запишите исходное значение и верните его в конце работы. Без пространства имён пользователей контейнер без привилегий построить нельзя.

## 3. Теория: границы изоляции ВМ и контейнера

**Две разные границы.** Гипервизор (в ПР1 — гипервизор второго типа на хосте) предоставляет ВМ виртуальное оборудование: процессоры, память, диски, сетевые адаптеры. Внутри ВМ работает собственное ядро, которое ничего не знает о процессах соседней ВМ. Граница изоляции ВМ — интерфейс гипервизора. Контейнер — это обычные процессы хоста, работающие на том же ядре. Ядро ограничивает их тремя группами механизмов. Пространства имён определяют, что процесс видит. Cgroups определяют, сколько ресурсов он потребляет. Привилегии (uid, capabilities, `no_new_privs`, seccomp, модули безопасности) определяют, что ему разрешено. Граница контейнера — системные вызовы ядра хоста. Ошибка в ядре или в конфигурации контейнера позволяет выйти за эту границу; для выхода из ВМ нужна уязвимость гипервизора.

**Пространства имён.** Каждое пространство имён изолирует один вид ресурсов ядра:

| Пространство | Что изолирует |
|---|---|
| mnt | дерево монтирования: корень, тома, `/proc` |
| uts | имя узла |
| ipc | очереди сообщений, семафоры, разделяемая память System V и POSIX |
| pid | нумерацию процессов: в контейнере свой PID 1, процессы хоста не видны |
| net | сетевой стек: интерфейсы, адреса, маршруты, порты, правила фильтрации |
| user | идентификаторы пользователей и групп и capabilities |
| cgroup | видимую процессу часть иерархии cgroup |

Принадлежность процесса показывают ссылки `/proc/PID/ns/*` вида `pid:[4026532268]`: одинаковый номер — одно и то же пространство. Номера сравнимы только в пределах одного ядра. У начальных пространств pid, user, uts, ipc и cgroup номера заданы константами ядра, поэтому на Astra и на Kali они совпадут, хотя это разные ядра и разные пространства. Что ядро одно, подтверждает `/proc/sys/kernel/random/boot_id` — случайный идентификатор, создаваемый при загрузке ядра.

**Пространство имён пользователей и отображение UID.** Строка `/proc/PID/uid_map` вида `0 100000 65536` означает: uid 0 внутри соответствует uid 100000 снаружи, всего отображено 65536 идентификаторов. Root контейнера на хосте — обычный пользователь 100000. Файл, созданный им на томе, на хосте принадлежит uid 100000. Файлы, владелец которых не отображён (например, root хоста), внутри видны как 65534 (nobody). Capabilities, полученные внутри пространства имён пользователей, действуют только на объекты этого пространства: на его сеть, его дерево монтирования, его имя узла и на файлы с отображёнными владельцами. Поэтому даже `CAP_DAC_OVERRIDE` в контейнере не открывает файл root хоста с правами 0600. Создаёт пространство имён пользователей привилегированная среда выполнения (так работает режим `userns-remap` в Docker) или, если ядро разрешает, сам обычный пользователь (rootless). В этой работе используется первый вариант: «без привилегий» означает без привилегий хоста.

**Capabilities, no_new_privs и seccomp.** Полномочия root разделены на capabilities (ПР3). Ограничивающее множество (bounding set) задаёт верхнюю границу: после `execve` процесс с uid 0 при пустом наследуемом множестве получает в разрешённое и действующее множества ровно ограничивающее множество. Если удалить из него всё, кроме нужного, ни одна программа в контейнере не получит лишнего. Docker по умолчанию оставляет 14 capabilities, в том числе `NET_RAW`; `--privileged` оставляет все и открывает устройства. Опасны прежде всего `SYS_ADMIN` (монтирование и десятки административных операций), `NET_ADMIN` (настройка сети), `NET_RAW` (сырые сокеты и подделка пакетов), `SYS_MODULE`, `SYS_PTRACE`. Флаг `no_new_privs` запрещает повышать права при `execve`: биты setuid/setgid и file capabilities игнорируются, поэтому `su` внутри такого контейнера не работает. Seccomp фильтрует сами системные вызовы. В учебной среде выполнения его нет; в Docker профиль по умолчанию запрещает несколько десятков вызовов. Отметьте это в отчёте как оставшийся пробел.

**Файловая система контейнера.** Среда выполнения создаёт пространство имён mnt, собирает в каталоге образа нужные монтирования (системные каталоги, тома, tmpfs, `/proc`) и делает этот каталог корнем вызовом `pivot_root`. Прежний корень после этого отмонтируется, и путей к файлам хоста не остаётся. `chroot` меняет только точку отсчёта путей: прежний корень остаётся смонтированным, а процесс с `CAP_SYS_CHROOT` может выйти из chroot. Тома (bind-монтирования) — сознательно открытые окна в файловую систему хоста. Если root контейнера равен root хоста, том с правом записи даёт полный доступ к его содержимому. Корень образа и справочные тома монтируют только для чтения, а записываемые части `/proc` (`/proc/sys` и др.) закрывают на запись.

**Сеть.** Новое сетевое пространство содержит только выключенный интерфейс `lo`: нет адресов, маршрутов и доступа наружу. Чтобы дать контейнеру сеть, среда выполнения создаёт пару veth, мост и правила NAT; в работе этого нет, у контейнера restricted сеть только внутренняя. Режим общей сети (`--network host` в Docker, контейнер shared здесь) отдаёт контейнеру стек хоста: его адрес, его порты, все его сети. ВМ получает сеть через виртуальный адаптер гипервизора; в ПР1 это Internal Network, которая соединяет только ВМ стенда.

**Ограничения ресурсов: cgroups.** Ограничения задаются файлами в иерархии cgroup, процесс помещается в группу записью PID в `cgroup.procs`, потомки наследуют группу.

| Ресурс | cgroup v1 | cgroup v2 | Реакция при превышении | Счётчик |
|---|---|---|---|---|
| Память | `memory.limit_in_bytes` | `memory.max` | освобождение страниц, затем OOM killer в группе: SIGKILL, код 137 | `memory.oom_control` (oom_kill), `memory.failcnt` / `memory.events` |
| Процессы | `pids.max` | `pids.max` | `fork()` возвращает EAGAIN, процесс не создаётся | `pids.events` (max) |
| CPU | `cpu.cfs_quota_us` / `cpu.cfs_period_us` | `cpu.max` | планировщик приостанавливает группу до следующего периода | `cpu.stat` (nr_throttled) |

Квота 20000 мкс на период 100000 мкс — 20 % одного ядра. Если учёт подкачки выключен (в ядрах Debian так по умолчанию, файлов `memory.memsw.*` нет), ограничение действует только на ОЗУ. Чтобы группа не уходила в подкачку, среда выполнения ставит ей `memory.swappiness = 0`: при достижении лимита группы это запрещает выгрузку. Ни cgroups, ни пространства имён не виртуализируют `/proc/meminfo` и число процессоров: программа в контейнере с лимитом 64 МБ видит весь объём памяти хоста и может рассчитать кэш на него.

**ВМ или контейнер.** ВМ выбирают, когда нагрузки разного уровня доверия должны быть разделены надёжной границей или нужно другое ядро. Контейнеры удобны для упаковки и тиражирования приложений одного уровня доверия; часто их запускают внутри ВМ. Для государственных систем требования к средствам виртуализации утверждены приказом ФСТЭК России № 187, к средствам контейнеризации — приказом № 118. В Astra Linux Special Edition изоляция контейнеров и ВМ дополняется мандатным управлением доступом и контролем целостности (лекция 10).

## 4. Индивидуальное задание

Каждый вариант получает требования к контейнеру учебной службы: имя узла, диапазон uid хоста для отображения root, набор capabilities, без которых служба не работает, лимиты памяти, процессов и CPU и порт приёмника на Kali. Профиль должен содержать **ровно** эти capabilities. Требования, общие для всех вариантов: пространства имён `mnt uts ipc pid net user` (`cgroup` рекомендуется), `user = 0`, `no_new_privs = yes`, `readonly_root = yes`, том `/data` ← `/srv/pr14/data` для записи, том `/hostdata` ← `/srv/pr14/host` только для чтения. `NET_RAW`, `SYS_ADMIN` и `NET_ADMIN` отсутствуют у всех.

### Шаг 4. Профиль контейнера без привилегий — 15 минут

Astra. Профиль составляется по таблицам 3 и 5; значения подставляются из параметров варианта:

```bash
HOST=$(python3 "$T" info --work "$W" --field hostname)
BASE=$(python3 "$T" info --work "$W" --field uid_base)
CAPS=$(python3 "$T" info --work "$W" --field caps_text)
MEM=$(python3 "$T" info --work "$W" --field memory_mb)
PIDS=$(python3 "$T" info --work "$W" --field pids)
CPU=$(python3 "$T" info --work "$W" --field cpu)
cat > profiles/restricted.ini <<EOF
# PR14 v$NN: контейнер учебной службы без привилегий хоста
[container]
hostname = $HOST
namespaces = mnt uts ipc pid net user cgroup
uid_map = 0 $BASE 65536
gid_map = 0 $BASE 65536
user = 0
capabilities = $CAPS
no_new_privs = yes
readonly_root = yes

[mounts]
/data = /srv/pr14/data rw
/hostdata = /srv/pr14/host ro

[limits]
memory = ${MEM}M
pids = $PIDS
cpu = $CPU%
EOF
cat profiles/restricted.ini
```

Сначала убедитесь, что скрипт ловит типичные ошибки: лишнюю опасную capability, отображение root на root и записываемый корень:

```bash
sed 's/^capabilities = .*/& SYS_ADMIN/; s/^uid_map = .*/uid_map = 0 0 65536/; s/^readonly_root = yes/readonly_root = no/' profiles/restricted.ini > profiles/bad.ini
sudo python3 "$T" profile-check --profile profiles/bad.ini --name bad | grep -E 'FAIL|не принят' | tee evidence/profile-bad.txt
sudo python3 "$T" profile-check --profile profiles/restricted.ini | tee evidence/profile-check.txt
```

Ожидание: для `bad.ini` — три строки FAIL (`uid_map`, `capabilities` с пометкой опасной `SYS_ADMIN`, `readonly_root`) и «Профиль не принят»; для `restricted.ini` все строки OK, включая проверки ядра, и «Профиль принят и зарегистрирован». После регистрации профиль не изменяйте: `run` сверяет его хеш. Изменили — повторите проверку. В отчёте обоснуйте каждую строку профиля: какую границу она создаёт и что будет без неё.

### Шаг 5. Контейнер без привилегий — 15 минут

Astra:

```bash
sudo python3 "$T" run --profile profiles/restricted.ini --label restricted --test probe
sudo ls -ln /srv/pr14/data | tee evidence/host-files-after-restricted.txt
sudo python3 "$T" run --profile profiles/restricted.ini --label restricted --test net

```

Ожидание для `probe`: hostname варианта; `uid_map` `0 100000·V 65536`; в действующем множестве ровно capabilities варианта; `NoNewPrivs=1`; все семь пространств имён свои. Видны два-три собственных процесса, из интерфейсов только `lo`, маршрутов нет. Секрет хоста — `denied`, хотя внутри процесс — root, а у части вариантов есть `DAC_OVERRIDE`; `secret_owner_inside` — `65534:65534`. Запись в `/hostdata` и в корень — `readonly`, в `/data` — `written`, а на хосте файл `probe-restricted.txt` принадлежит uid `100000·V`. Проверки привилегий: capabilities варианта — `allowed`, остальные — `denied`. Сетевая проба — `unreachable` (ENETUNREACH), приёмник на Kali нового подключения не получает. Команда `restricted-cmd` показывает то же изнутри: `su` не повышает права (действует `no_new_privs`), запись в `/etc` отклоняется (Read-only file system).

Промежуточный процесс среды выполнения не имеет capabilities. В cgroup действуют лимиты варианта. Сравните с шагом 3: одни и те же программы, одно ядро, разные границы.

| resources | ограничено ли потребление ресурсов отдельно от Astra | лимиты cgroup, run-*-mem/pids/cpu.json |
| meminfo | видит ли контекст свой объём памяти, а не объём Astra | MemTotal |

```bash
python3 "$T" assess --work "$W"
```

`assess` сравнивает таблицу с измерениями и сохраняет результат. Расхождения разберите в отчёте: исправлять таблицу после `assess` можно, но первый результат остаётся в отчёте.

Итоговая проверка, удаление учебных объектов и суммы:

```bash
sudo python3 "$T" check
sudo python3 "$T" cleanup --yes
sha256sum evidence/* > SHA256SUMS.txt
sha256sum session.json isolation.csv profiles/*.ini >> SHA256SUMS.txt
sha256sum -c SHA256SUMS.txt
```

Ожидание: `check` — все строки OK и `passed: True`. Проверяются: профиль не менялся; граница ВМ (другой boot_id, файлов Astra на Kali нет); у shared root равен root хоста и секрет прочитан; у restricted — отображение uid, ровно разрешённые capabilities и результаты всех девяти проверок привилегий, `no_new_privs`, файловые ограничения, шесть своих пространств имён. Также проверяются сеть (shared — `connected`, restricted — `unreachable`) и подключение с адреса Astra в журнале Kali, все три лимита и сравнение с shared, наблюдение за обоими контейнерами, выполненный `assess`. `cleanup` останавливает оставшиеся контейнеры, удаляет группы cgroup `pr14`, образ, `/srv/pr14`, `/run/pr14` и показывает `"clean": true`. Если на шаге 2.3 добавлялось правило межсетевого экрана, удалите его; если изменялся `user.max_user_namespaces`, верните исходное значение.

Таблица 9 — Типовые затруднения

| Симптом | Проверить и сделать |
|---|---|
| init: ядро не поддерживает пространства имён | Ядро без `CONFIG_USER_NS`/`CONFIG_PID_NS`: обратитесь к преподавателю, не меняйте ядро самостоятельно |

| run: метка shared: используйте неизменённый shared.ini | Файл изменён; восстановите из снимка или выполните cleanup и init заново |
