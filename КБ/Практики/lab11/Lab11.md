# Практическая работа № 11. Проверка уязвимостей конфигурации и обновлений

**Дисциплина:** Операционные системы. **Специальность:** 10.05.01 «Компьютерная безопасность», университет, 3-й курс. **Продолжительность:** 90 минут; подготовка пакетов и снимков выполняется заранее. **Варианты:** 27, номер соответствует номеру студента по списку в журнале.

Тема взята из раздела 4.2 РПД: сканирование учебного узла разрешённым средством Kali Linux, анализ только подтверждённых результатов, проверка версий пакетов, безопасное обновление и контрольная повторная проверка. Теоретическая основа — тема 12 РПД об обновлениях и цепочке поставок: репозитории, подписи пакетов, зависимости, жизненный цикл обновлений и откат.

**Вариант для предоставленного «Орла» 2.12.22:** Astra Linux Common Edition «Орёл» 2.12.22 (Python 3.5, APT 1.4, dpkg 1.18, systemd 232) и Kali Linux из стенда ПР1. Обновляется **учебный пакет pr11-demo** из локального репозитория, подписанного учебным ключом. Для этого в изолированной сети не нужен внешний доступ. Kali выполняет только ограниченные проверки одного порта своей Astra: `nmap -sV` и короткую серию GET-запросов скриптом комплекта.

**Граница результата:** находки OSLAB-2026-11xx — учебные, это не CVE и не сведения о реальном продукте. Штатные пакеты Astra в этой работе только проверяются по версиям и **не обновляются**: полное обновление ОС выполняется из официального источника того же выпуска по регламенту организации. Удалённый результат по баннеру — гипотеза, а не доказательство. Подтверждение выполняется локально: версия пакета, конфигурация, версия работающего процесса.

## 1. Цель и результаты

Цель — пройти полный цикл «обнаружение → подтверждение → безопасное обновление → повторная проверка» и для каждой находки обосновать, какие факты её подтверждают, а какие только допускают.

Задачи: проверить готовность стенда и версии штатных пакетов; проверить цепочку доверия учебного репозитория и бюллетеня; убедиться, что APT отвергает источник с чужой подписью; установить исходную версию учебной службы и выполнить ограниченное сканирование с Kali; подтвердить или опровергнуть каждую находку локально; выбрать целевую версию по политике варианта, проверить пакет до установки, смоделировать и выполнить обновление; повторить проверки до и после перезапуска службы; построить таблицу находок; удалить учебные изменения и доказать восстановление.

Результат — исходные JSON/JSONL-файлы обеих VM, вывод nmap, таблица findings.csv, сопоставление удалённых и локальных результатов, обоснование выбора версии и подтверждение очистки. Не объявляйте уязвимость устранённой только потому, что изменился номер версии, и не объявляйте её существующей только по баннеру.

### 2.1. Проверка программ и комплекта

На Astra, Bash, обычная учебная запись:

```bash
cat /etc/os-release
cat /etc/astra_version 2>/dev/null
uname -r
python3 --version
apt-get --version | head -n 1
dpkg --version | head -n 1
for c in apt-get apt-cache dpkg-query dpkg-deb gpgv systemd-run systemctl journalctl python3 ip sha256sum zcat tar sudo; do
    command -v "$c" || printf 'ОТСУТСТВУЕТ: %s\n' "$c"
done
cd "$HOME/pr11/kit" && sha256sum -c SHA256SUMS.txt | grep -v ': OK$'; cd "$HOME/pr11" || exit
```

На Kali, Bash, обычная запись:

```bash
cat /etc/os-release
nmap --version | head -n 1
python3 --version
for c in nmap python3 gpgv ip sha256sum; do
    command -v "$c" || printf 'ОТСУТСТВУЕТ: %s\n' "$c"
done
cd "$HOME/pr11/kit" && sha256sum -c SHA256SUMS.txt | grep -v ': OK$'; cd "$HOME/pr11" || exit
```

Ожидание: команды найдены; проверка сумм не выводит строк, то есть все файлы OK. Если сумма не совпала, файл повреждён или изменён: получите комплект заново, не продолжайте с ним. Сохраните выводы для отчёта.

## 3. Теория: от находки сканера к подтверждённому выводу

**Удалённая проверка видит только поведение снаружи.** nmap с `-sV` отправляет пробы и сравнивает ответы с базой сигнатур. Если служба не опознана, версия видна лишь в сыром ответе (`fingerprint-strings`). Версия из заголовка Server — утверждение самой программы: его можно изменить, а исправление его не обязательно меняет. Совпадение версии с бюллетенем даёт статус «возможно» (POSSIBLE_BY_VERSION). Наблюдаемое поведение, например ответ 200 с конфигурацией на `/debug`, — более сильный факт (OBSERVED), но и он не говорит, какой пакет установлен и почему.

**Версия пакета Debian/Astra** имеет вид `upstream-revision`, например `1.0-2`. Поставщик часто переносит исправление в старую ветку (бэкпорт): upstream остаётся 1.0, меняется только ревизия. Баннер `PR11Demo/1.0` не различает 1.0-1 и 1.0-2, поэтому сканер по версии даёт ложное срабатывание после исправления. Решение принимают по локальной версии (`dpkg-query`), changelog пакета и фактическому поведению.

**Цепочка доверия APT.** Ключ архива проверяет подпись InRelease (или Release.gpg для Release). В Release записаны SHA256 и размеры индексов Packages. В Packages записаны SHA256 и размеры файлов .deb. Если любое звено не совпадает, пакет не считается доверенным. Опция `signed-by` в строке источника ограничивает доверие одним ключом и одним источником; ключ не добавляется в общее хранилище `/etc/apt/trusted.gpg.d`. Опции `trusted=yes`, `--allow-unauthenticated` и `AllowInsecureRepositories` отключают эту защиту и в работе запрещены. Отпечаток ключа сверяется по независимому каналу — здесь по тексту задания:

```text
Учебный ключ архива OS Lab: 5DFE 8889 5F0C 7932 597E  6B4D 770F AA1F BFFF 93BE
```

**Безопасное обновление** — это управляемое изменение, а не команда upgrade. Порядок: точка отката (снимок); проверенный источник; выбор конкретной версии по политике; загрузка и проверка пакета до установки (хеш, control, changelog); моделирование `apt-get -s`, где нет удаления посторонних пакетов; установка указанной версии; проверка файлов `dpkg -V`; перезапуск зависимых процессов; повторная проверка. Кандидат APT — самая новая доступная версия, а не обязательно нужная: в варианте A требуется минимальный бэкпорт 1.0-2, хотя кандидат — 1.1-1.

**Конфигурационные файлы (conffiles)** dpkg не перезаписывает молча, если администратор их изменил. Неизменённый conffile заменяется версией из нового пакета. Поэтому в работе учебный conffile не редактируется.

**Обновлённый пакет не меняет уже работающий процесс.** dpkg заменяет файлы на диске, а запущенный интерпретатор продолжает выполнять загруженный старый код. До перезапуска удалённая проверка показывает прежнее поведение, а локальный аудит — `restart_required=true`. В реальной системе то же относится к службам после обновления библиотек.

Таблица 3 — Статусы и сила вывода

| Статус | Источник | Смысл |
|---|---|---|
| OBSERVED | Kali | Поведение наблюдалось удалённо; причина и версия пакета не установлены |
| POSSIBLE_BY_VERSION | Kali | Версия баннера входит в affected_upstream; требуется подтверждение |
| NOT_FLAGGED | Kali | По баннеру и удалённым проверкам находки нет; это не доказательство отсутствия |

| NOT_APPLICABLE | Astra | Работающая версия не относится к затронутым |

Группа A: после обновления и перезапуска баннер остаётся `PR11Demo/1.0`, удалённая проверка по версии по-прежнему пишет «возможно», а локально находки 1101 и 1102 не подтверждаются — это ложное срабатывание по версии. ### Шаг 1. Сессия, параметры и штатные версии — 10 минут

Astra, Bash, обычная запись. Если работа уже выполнялась, сохраните прежний `$HOME/pr11` под другим именем и подготовьте новый с каталогом kit. В основном терминале:

```bash
cd "$HOME/pr11" || exit
V=1
python3 kit/tools/pr11.py init --work "$HOME/pr11" --variant "$V" > evidence-init.json
```

Замените 1 своим вариантом. init создаёт session.json, каталоги evidence, state, apt и два файла списка источников. Существующую сессию он не затирает. Если паспорт отличается, добавьте `--astra АДРЕС --kali АДРЕС`. Затем в том же терминале:

```bash
W="$HOME/pr11"
T="$W/kit/tools/pr11.py"
RUN_ID=$(python3 "$T" info --work "$W" --field run)
PORT=$(python3 "$T" info --work "$W" --field port)
ASTRA_IP=$(python3 "$T" info --work "$W" --field astra)
KALI_IP=$(python3 "$T" info --work "$W" --field kali)
TARGET=$(python3 "$T" info --work "$W" --field target_version)
UNIT=$(python3 "$T" info --work "$W" --field unit)
START=$(python3 "$T" info --work "$W" --field since)
APT_LAB="-o Dir::Etc::SourceList=$W/apt/oslab11.list -o Dir::Etc::SourceParts=- -o APT::Get::List-Cleanup=0"
printf 'V=%s run=%s Astra=%s Kali=%s port=%s target=%s\n' "$V" "$RUN_ID" "$ASTRA_IP" "$KALI_IP" "$PORT" "$TARGET" | tee evidence/parameters.txt
ip -4 address show | tee evidence/addresses.txt
ip -4 route | tee evidence/routes-v4.txt
ip -6 route | tee evidence/routes-v6.txt
ip -4 route get "$KALI_IP" | tee evidence/peer-route.txt
```

Переменные действуют только в этом терминале; держите его открытым. APT_LAB намеренно подставляется без кавычек: это три параметра. Они заставляют APT использовать **только** учебный список источников, не читать `/etc/apt/sources.list.d` и не удалять списки штатных источников. Путь домашнего каталога не должен содержать пробелов.

Проверка версий штатного пакета варианта (P из таблицы 4) — только чтение, без `apt-get update` штатных источников:

```bash
P=bash
dpkg-query -W -f='${Package}\t${Version}\t${Status}\n' "$P" | tee evidence/system-package.txt
apt-cache policy "$P" | tee -a evidence/system-package.txt
```

В отчёте укажите Installed, Candidate и источник кандидата (ISO, сетевой репозиторий, только `/var/lib/dpkg/status`). Если Candidate совпадает с Installed, обновления из **настроенных доверенных** источников нет. Это не означает отсутствие уязвимостей: сведения устаревают с датой списков, а сравнение с бюллетенями поставщика требует официального источника того же выпуска. Если пакета нет, зафиксируйте это.

### Шаг 2. Цепочка доверия репозитория и бюллетеня — 15 минут

Astra, основной терминал. Разместите копию репозитория в общем каталоге, доступном служебной записи APT для чтения. Каталог `/srv/oslab11` не должен существовать заранее:

```bash
test ! -e /srv/oslab11 || echo 'СТОП: /srv/oslab11 уже существует, выясните происхождение'
sudo install -d -m 0755 /srv/oslab11
sudo cp -R --no-preserve=mode,ownership kit/repo/. /srv/oslab11/
sudo chmod -R a+rX,go-w /srv/oslab11
python3 "$T" repo-verify --repo /srv/oslab11/orel-lab --suite orel-lab --output evidence/repo-trusted.json
gpgv --keyring /srv/oslab11/keys/oslab11-archive.gpg /srv/oslab11/orel-lab/dists/orel-lab/InRelease 2>&1 | tee evidence/gpgv-inrelease.txt
python3 "$T" advisory --file /srv/oslab11/advisories/OSLAB-2026-11.json | tee evidence/advisory.txt
```

Ожидание: все строки repo-verify — OK, итог TRUSTED; gpgv сообщает Good signature, а отпечаток совпадает с указанным в разделе 3. Бюллетень подписан тем же ключом и содержит три находки. Скрипт сверяет отпечаток с константой; сравните его и глазами. Ключ из того же носителя без сверки отпечатка доказывает только целостность копии.

Подключите доверенный источник **без изменения системных списков**:

```bash
cat "$W/apt/oslab11.list"
sudo apt-get $APT_LAB update 2>&1 | tee evidence/apt-update-trusted.txt
apt-cache $APT_LAB policy pr11-demo | tee evidence/policy-initial.txt
```

Ожидание: строка `deb [signed-by=/srv/oslab11/keys/oslab11-archive.gpg] file:/srv/oslab11/orel-lab orel-lab main`; update без ошибок; в таблице версий — 1.1-1, 1.0-2, 1.0-1, Candidate 1.1-1, Installed (none).

Проверьте источник «срочного исправления» 9.9-1:

```bash
python3 "$T" repo-verify --repo /srv/oslab11/untrusted --suite orel-hotfix --output evidence/repo-hotfix.json; echo "repo-verify code=$?"
cat "$W/apt/hotfix.list"
sudo apt-get -o Dir::Etc::SourceList="$W/apt/hotfix.list" -o Dir::Etc::SourceParts=- -o APT::Get::List-Cleanup=0 update 2>&1 | tee evidence/apt-update-hotfix.txt
apt-cache -o Dir::Etc::SourceList="$W/apt/hotfix.list" -o Dir::Etc::SourceParts=- policy pr11-demo | tee evidence/policy-hotfix.txt
```

Ожидание: repo-verify показывает FAIL для подписей, хотя хеши индексов и пакета совпадают, и завершается с кодом 3. APT сообщает NO_PUBKEY E41D19509CBA835E и ошибку «repository … is not signed», код 100. Версия 9.9-1 не становится кандидатом. Объясните, почему совпадение хешей не делает источник доверенным. **Не** добавляйте посторонний ключ, `trusted=yes` или `--allow-unauthenticated`: это и есть атака на цепочку поставок.

### Шаг 3. Исходное состояние и сканирование — 15 минут

Astra, основной терминал. Смоделируйте и установите исходную версию:

```bash
sudo apt-get $APT_LAB -s install pr11-demo=1.0-1 | tee evidence/simulate-install.txt
sudo apt-get $APT_LAB install pr11-demo=1.0-1
dpkg-query -W -f='${Package} ${Version} ${Status}\n' pr11-demo | tee evidence/dpkg-before.txt
stat -c '%A %U:%G %n' /etc/pr11-demo/pr11-demo.conf | tee -a evidence/dpkg-before.txt
```

Моделирование должно показать только `Inst pr11-demo (1.0-1 …)` и `Conf`, без Remv. Если предлагается удалить другие пакеты, остановитесь и разберите причину с преподавателем.

Запустите службу временным unit **с правами обычной записи**. Функция нужна, чтобы позже перезапустить службу с теми же параметрами:

```bash
start_demo() {
  sudo systemd-run --unit="$UNIT" --uid="$(id -un)" --gid="$(id -gn)" \
    --property=StandardOutput=journal --property=StandardError=journal \
    --property="SyslogIdentifier=$UNIT" \
    /usr/bin/python3 -u /usr/lib/pr11-demo/pr11_demo.py --bind "$ASTRA_IP" --port "$PORT" \
    --peer "$KALI_IP" --run "$RUN_ID" --state "$W/state"
}
start_demo
sleep 2
sudo journalctl -b -u "$UNIT.service" -n 5 --no-pager -o cat
systemctl show "$UNIT.service" -p User -p Group -p MainPID | tee evidence/unit.txt
ss -lntp "sport = :$PORT" | tee evidence/port-running.txt
```

Ожидание: SERVER_READY с `build 1.0-1` и `debug_active true`; один LISTEN на адресе Astra; User — ваша учебная запись. Служба отвечает только своей Kali и самой Astra.

Kali, Bash, обычная запись, `$HOME/pr11`. RUN_ID скопируйте **точно** из evidence/parameters.txt Astra:

```bash

python3 kit/tools/pr11_check.py --host "$ASTRA_IP" --variant "$V" --run "$RUN_ID" \
  --phase before --advisory "$ADV" --output evidence/check-before.jsonl
```

Единственная цель — своя Astra, единственный порт — порт варианта. Не сканируйте подсеть, не добавляйте скрипты NSE категорий vuln/intrusive/brute, не перебирайте пути. Ожидание nmap: порт open; служба может быть показана как unknown, тогда заголовок `Server: PR11Demo/1.0` виден в `fingerprint-strings`. Ожидание скрипта: valid=True, 1101 — OBSERVED (ключи конфигурации debug, token; значения не сохраняются), 1102 — POSSIBLE_BY_VERSION без удалённой проверки, 1104 — NOT_FLAGGED.

Astra, основной терминал — локальное подтверждение:

```bash
python3 "$T" audit --work "$W" --phase before
grep -c '^token' /etc/pr11-demo/pr11-demo.conf
```

Ожидание: 1101 и 1102 — CONFIRMED, 1104 — NOT_APPLICABLE; права conffile 0644 при наличии ключа token. Значение токена не выводите и не копируйте в отчёт: `grep -c` считает строки. Если служба недоступна с Kali из-за сохранённой политики ПР8, не меняйте firewall в этой работе — используйте с преподавателем исходный снимок, где учебная связь разрешена.

Ожидание: `Inst pr11-demo [1.0-1] (ЦЕЛЕВАЯ …)` и `Conf`, без Remv и без других пакетов. В варианте A объясните, почему не выбран кандидат 1.1-1; в варианте B — почему переход на ветку допустим по политике. Выполните обновление и проверьте файлы:


Ожидание: OK для каждого файла. Если очистка не подтверждена, сохраните доказательства вне VM и верните снимок с преподавателем; снимок не заменяет объяснение причины.
