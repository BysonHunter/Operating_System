## 3. Краткая теория

Аутентификация проверяет личность, а этап account проверяет допустимость использования учётной записи. Успешная проверка пароля ещё не гарантирует разрешённый вход: возможны ограничения срока действия, SSH и политики Astra Linux.

PAM разделяет обработку на `auth`, `account`, `password` и `session`. Поле управления определяет реакцию на результат модуля. `required` сохраняет ошибку и продолжает стек; `requisite` прекращает обработку при ошибке; `sufficient` может завершить стек успехом при отсутствии предыдущих обязательных ошибок. Расширенное правило `success=1` пропускает следующую строку при успехе. `substack` ограничивает действия внутренних управляющих правил рамками вложенного стека.

`pam_pwquality` действует при **смене** пароля. Он не проверяет заново качество уже установленного пароля при каждом входе. В работе нулевые credits исключают бонусы к длине, а `minclass` задаёт число классов символов. `maxrepeat` ограничивает одинаковые символы подряд. Дополнительные проверки словаря могут отклонить пароль, удовлетворяющий только числовым требованиям; это не ошибка политики.

`pam_faillock`: `preauth` проверяет текущую блокировку, `authfail` учитывает неудачу, `authsucc` сбрасывает накопленные неудачи после успешной аутентификации. `deny=D` — порог, `fail_interval=I` — окно учёта, `unlock_time=U` — длительность блокировки. Параметры задаются в секундах. Файлы счётчиков и журнал событий — разные источники доказательств.

Блокировка учётной записи после серии неудач может использоваться для отказа в доступе её владельцу. Поэтому числа вариантов предназначены для короткого учебного опыта; выбор производственной политики требует отдельного обоснования.

### 6.1. Исходное состояние и резервная копия

Все изменения на Astra выполняйте из её консоли. Установите номер своего варианта; далее примеры переменных рассчитаны на одну Bash-сессию:

```bash
V=1                          # замените номером своего варианта
printf -v NN '%02d' "$V"
U_NAME="lab06$NN"
WORK="$HOME/oslab/lab06-V$NN"
mkdir -p "$WORK"

sudo install -d -m 700 "$BACKUP"
sudo cp -a /etc/pam.d "$BACKUP/pam.d"
sudo cp -a /etc/ssh/sshd_config "$BACKUP/sshd_config"

```

Если каталог `sshd_config.d` отсутствует, зафиксируйте это; ошибка последней команды не отменяет другие копии. Копия PAM нужна **до** запуска pam-auth-update. Не используйте существующий каталог резервной копии повторно.

Проверьте отсутствие записи командой `getent passwd "$U_NAME"`. Если запись уже есть, выясните её происхождение и используйте чистый снимок; не удаляйте неизвестного пользователя. Создайте новую локальную запись:

```bash
sudo useradd -m -s /bin/bash "$U_NAME"
sudo passwd "$U_NAME"
sudo chage -l "$U_NAME"
sudo systemctl status ssh --no-pager
```

Назначьте самостоятельно уникальный учебный пароль; ввод только интерактивный. Не добавляйте пользователя в sudo. Если политика Astra требует метку/уровень для нового пользователя, преподаватель назначает допустимый учебный профиль штатными средствами. Не отключайте MAC.

Укажите на Kali адрес Astra из паспорта стенда и имя пользователя:

```bash
ASTRA_IP='АДРЕС_ИЗ_ПАСПОРТА'
LAB_USER='lab0601'             # замените своим именем
ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password \
    -o NumberOfPasswordPrompts=1 "$LAB_USER@$ASTRA_IP"
```

При первом соединении сверьте отпечаток ключа сервера с консолью Astra (`sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`, если используется этот ключ). Не отключайте проверку ключа хоста. Выполните `id`, затем `exit`. Это исходный успешный вход.

### 6.2. Качество нового пароля

Если профиль pwquality ещё не включён, на Astra запустите `sudo pam-auth-update`, включите проверку качества паролей и сохраните уже включённые профили. Не снимайте флажки модулей Astra. Преподаватель проверяет итоговый `/etc/pam.d/common-password`: модуль качества должен находиться перед `pam_unix`, а `pam_unix` должен использовать `use_authtok`, сохраняя остальные параметры своей редакции.

Отредактируйте **существующую** строку `pam_pwquality.so`: замените конфликтующие параметры и задайте свои L, C, R. Пример для варианта 1:

```text
password requisite pam_pwquality.so retry=1 minlen=12 minclass=3 maxrepeat=2 dcredit=0 ucredit=0 lcredit=0 ocredit=0 enforce_for_root
```

Остальные строки не заменяйте. Если pwquality уже вызван несколько раз, преподаватель устраняет дублирование до эксперимента. Параметры строки приоритетнее одноимённых настроек файла конфигурации. `enforce_for_root` нужен потому, что тесты выполняются через `sudo passwd`.

Четырежды отдельно вызовите `sudo passwd "$U_NAME"`:

1. Кандидат короче L, остальные требования соблюдены.
2. Кандидат длиной не менее L, но с числом классов C−1.
3. Кандидат длиной не менее L и с C классами, но с R+1 одинаковыми символами подряд.
4. Кандидат длиной L+4 или больше, с четырьмя классами, без длинных повторов, последовательностей и словарных слов.

Для отрицательных тестов меняйте только проверяемое свойство, насколько это позволяет словарная проверка. Используйте ASCII для однозначного подсчёта длины и классов. При `retry=1` отказ завершит текущую смену; предыдущий пароль останется действовать. Последний кандидат должен быть принят и станет паролем для SSH-проверок. Если отказ вызван другой проверкой, запишите реальную причину и скорректируйте кандидат. В отчёте укажите свойства кандидатов и сообщения, но не сами пароли.

### 6.3. Временная блокировка только учебного SSH-пользователя

Введите значения D, I и U своего варианта. Ниже пример для варианта 1:

```bash
D=3
I=300
U=60
```

Сначала прочитайте действующие `/etc/security/faillock.conf` и локальную страницу `man pam_faillock`. Если там включена блокировка root или уже есть несовместимая политика, преподаватель готовит отдельный профиль; следующий шаблон не применяется вслепую.

Создайте вложенный auth-стек:

```bash
sudo tee /etc/pam.d/lab06-auth >/dev/null <<EOF
auth required pam_faillock.so preauth silent deny=$D fail_interval=$I unlock_time=$U
auth [success=1 default=bad] pam_unix.so
auth [default=die] pam_faillock.so authfail deny=$D fail_interval=$I unlock_time=$U
auth sufficient pam_faillock.so authsucc deny=$D fail_interval=$I unlock_time=$U
auth required pam_deny.so
EOF
sudo chmod 644 /etc/pam.d/lab06-auth
```

В `/etc/pam.d/sshd` замените **единственную** строку `@include common-auth` следующим блоком. Имя замените своим реальным `lab06NN`; переменные Bash здесь не подставляются:

```text
auth [success=1 default=ignore] pam_succeed_if.so user != lab0601 quiet
auth [success=1 default=die] substack lab06-auth
@include common-auth
```

Для остальных пользователей первая строка пропускает вложенный стек и используется прежний common-auth. Для учебного пользователя выполняется вложенный стек; при его успехе пропускается common-auth, поэтому второй пароль не запрашивается. Ошибка вложенного стека завершает auth отказом. Существующие `account`, `password`, `session` и другие строки SSH PAM-файла сохраняются. Этот маршрут проверяет локальный UNIX-пароль; он допустим только в подготовленном профиле совместимости из раздела 2.

**Проверка SSH.** Для выбранного пользователя нужны эффективные `UsePAM yes`, `PasswordAuthentication yes`, отсутствие требования дополнительного метода в `AuthenticationMethods` и разрешённый вход согласно AllowUsers/AllowGroups. Проверьте:

```bash
sudo sshd -t
sudo sshd -T -C user="$U_NAME",host=kali,addr=АДРЕС_KALI \
  | grep -E 'usepam|passwordauthentication|authenticationmethods|maxauthtries|allowusers|allowgroups'
```

Подставьте действительный адрес Kali. `sshd -t` проверяет конфигурацию SSH, **не корректность PAM**. Если парольный вход для учебного пользователя запрещён, преподаватель добавляет ограниченное этим пользователем исключение в SSH-конфигурацию и проверяет его той же командой. Глобальные ограничения существующих пользователей не ослабляются. При изменении SSH после успешного `sshd -t` выполните `sudo systemctl reload ssh`. При изменении только PAM перезагрузка sshd не нужна.

Перед серией из консоли выполните:

```bash
sudo faillock --user "$U_NAME" --reset
sudo faillock --user "$U_NAME"
date --iso-8601=seconds | tee "$WORK/test-start.txt"
```

Проверьте один правильный вход из Kali. Если он не работает, не начинайте серию ошибок: выясните причину по журналу и резервной копии.

### 6.4. Проверка порога и восстановления

Используйте ту же команду SSH из раздела 6.1. Каждый запуск содержит один парольный запрос; вводите пароль вручную. Не применяйте словари, Hydra, sshpass и автоматический перебор.

| Шаг | Действие из Kali | Проверка в консоли Astra | Ожидание |
|---|---|---|---|
| A | Один неверный вход | `faillock --user ИМЯ` | Появилась неудача |
| B | Один правильный вход | Снова вывести счётчик | Вход успешен, прежняя неудача сброшена |
| C | D отдельных неверных входов, без успешных между ними | Проверять счётчик после каждого | Накапливаются действующие неудачи |
| D | Один правильный вход сразу после D-й неудачи | Счётчик и журнал | Вход отклонён из-за блокировки |
| E | После U секунд от момента достижения порога один правильный вход | Счётчик и журнал | Доступ восстановлен, счётчик сброшен |
| F | Один неверный вход, затем сброс из консоли и правильный вход | `faillock --user ИМЯ --reset` | Подтверждено ручное восстановление |

Шаги C и D завершите внутри I секунд. Отсчитывайте U от порогового события, фиксируя время; можно выждать U+5 секунд по часам. Не перезагружайте VM между D и E: очистка временных файлов счётчика сделает проверку недостоверной. Не отправляйте дополнительные попытки во время ожидания.

Одна попытка здесь — один фактический обмен паролем. Сетевой отказ без парольного запроса не считается неудачной аутентификацией. `MaxAuthTries` ограничивает попытки в одном SSH-соединении; это другой механизм.

Вся работа требует не более D+2 неправильных паролей, то есть максимум 7. При неожиданном росте счётчика остановите проверки и найдите причину: повторные запросы, другой метод аутентификации, параллельный сеанс или неверное PAM-правило.

### 6.5. Журналы и доказательства

Время начала возьмите из `test-start.txt`. На Astra:

```bash
START=$(cat "$WORK/test-start.txt")
sudo journalctl -u ssh --since "$START" --no-pager > "$WORK/ssh-journal.txt"
sudo journalctl --since "$START" --no-pager \
  | grep -E "sshd|pam_faillock|$U_NAME" > "$WORK/auth-events.txt"
sudo faillock --user "$U_NAME" > "$WORK/faillock-final.txt"
sudo cp /etc/pam.d/lab06-auth "$WORK/pam-lab06-auth.txt"
sudo cp /etc/pam.d/sshd "$WORK/pam-sshd.txt"
sudo grep -nE 'pam_pwquality|pam_unix' /etc/pam.d/common-password \
  > "$WORK/password-policy.txt"
```

Если unit называется иначе, используйте название из `systemctl status`. Если события не попали в journald, проверьте `/var/log/auth.log`; сохраните только строки периода эксперимента с учебным пользователем. Не отключайте аудит Astra. Формулировки сообщений и детализация зависят от редакции: одинаковая надпись SSH «Permission denied» сама по себе не доказывает блокировку.

Сохраните промежуточные выводы `faillock` после A, B, каждой C и D в отдельные текстовые файлы: финальный пустой счётчик не заменяет свидетельство достижения порога. Зафиксируйте версию ОС, фактическую конфигурацию и временные отметки на двух узлах; при расхождении часов учитывайте поправку.

### 6.6. Восстановление

Сначала сохраните доказательства **за пределы откатываемого диска VM** разрешённым способом из работы № 1. Преподаватель проверяет, что файлы доступны. После этого восстановите снимок `pre-lab06-VNN`: он возвращает PAM, SSH и пользователей вместе с состоянием пакетов. Убедитесь, что исходный административный вход работает, а временная запись отсутствует, если её не было до работы.

Если преподаватель требует сохранить настроенный стенд, вместо отката создаётся отдельный снимок `lab06-policy-VNN`; исходный снимок остаётся доступным. Такой выбор укажите в отчёте. Для аварийного восстановления используйте консоль и исходную резервную копию либо откат снимка. Не закрывайте единственный работающий административный сеанс до проверки восстановления.

## 9. Типовые ошибки

| Симптом | Вероятная причина | Проверка/исправление |
|---|---|---|
| root назначает слабый пароль | Нет enforce_for_root или модуль не вызван | Проверить активную строку и порядок password-стека |
| Пароль неожиданно отклонён | Словарь, последовательность или другой активный модуль | Записать реальную причину; проверить локальную документацию |
| Правильный пароль не принимается до опыта | SSH-ограничение, срок записи, метка Astra, ошибочный PAM | Консоль, chage, sshd -T, журнал; не накапливать ошибки |
| Неудачи не учитываются | PAM отключён, обойдён authfail, другой метод входа | Проверить эффективный UsePAM и actual auth-стек |
| Два парольных запроса | Не пропущен common-auth после substack | Проверить управляющие правила и имя пользователя |
| Счётчик больше числа запусков | Несколько запросов/сеансов | NumberOfPasswordPrompts=1, отключить publickey на клиенте |
| «Блокировка» исчезла после перезагрузки | Временное хранилище счётчиков | Повторить опыт без перезагрузки |
| Нет сообщения о блокировке | silent или другая детализация журнала | Сопоставить конфигурацию, счётчик, время и отказ |
