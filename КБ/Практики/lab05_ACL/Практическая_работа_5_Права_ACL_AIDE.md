## 4. Краткие теоретические сведения

### 4.1. Базовые права доступа

Для обычного файла право `r` разрешает чтение, `w` — изменение содержимого, `x` — выполнение. Для каталога смысл отличается: `r` позволяет получить список имён, `w` — создавать и удалять записи каталога, а `x` — проходить через каталог и обращаться к объекту по известному имени.

Проверка выполняется последовательно: ядро определяет применимую категорию субъекта и вычисляет эффективные права. В традиционной модели используются владелец, группа-владелец и остальные пользователи. Команда `chmod 640 file` задаёт права `rw-r-----`, а `chmod 750 dir` — `rwxr-x---`.

### 4.2. ACL

ACL расширяет базовую модель и позволяет назначать права отдельному пользователю или группе без смены владельца. Команда `getfacl` выводит ACL, а `setfacl` изменяет её. Запись `user:oslab5_reader:r--` предоставляет указанному пользователю чтение обычного файла.

**ACL mask** ограничивает эффективные права именованных пользователей, именованных групп и группы-владельца. Поэтому запись может содержать `rw-`, но фактическое право оказаться `r--`, если mask запрещает запись. В выводе `getfacl` это отмечается комментарием `#effective:`.

ACL по умолчанию назначается каталогу и наследуется создаваемыми внутри него объектами. Она не изменяет ранее существовавшие файлы.

### 4.3. Контроль целостности

Контрольная сумма позволяет проверить содержимое одного файла, но не описывает всю совокупность ожидаемых объектов и их метаданные. AIDE создаёт базу доверенного состояния и затем сравнивает с ней текущее состояние. Политика определяет контролируемые пути и атрибуты: тип, права, UID, GID, размер, временные метки, контрольную сумму и ACL.

Сообщение AIDE об изменении не доказывает атаку. Оно означает, что наблюдаемое состояние отличается от принятого эталона. Администратор должен определить причину, подтвердить допустимость изменения, восстановить объект при необходимости и только после проверки обновить эталон.

### 4.4. Почему проверяются и запрет, и разрешение

Один успешный доступ не доказывает корректность политики. Необходимо показать как минимум одну разрешённую и одну запрещённую операцию. Проверка выполняется командой `sudo -u ИМЯ -- КОМАНДА`, поэтому пароль тестовой учётной записи не требуется и интерактивный сеанс не создаётся.

## 7. Пошаговое выполнение

### Шаг 1. Восстановите доверенное состояние и подготовьте каталог результатов

Восстановите snapshot `clean-VNN`. Войдите под своей обычной учётной записью и задайте параметры варианта:

```bash
export V=НОМЕР_ВАРИАНТА
export MODE=ЗНАЧЕНИЕ_ИЗ_ТАБЛИЦЫ
export ACL_PROFILE=ПРОФИЛЬ_ИЗ_ТАБЛИЦЫ
export EVENT=СОБЫТИЕ_ИЗ_ТАБЛИЦЫ

export LAB="$HOME/oslab/lab05"
export EVIDENCE="$LAB/evidence"
export LABROOT="/srv/oslab-lab05-$USER"
export SECURE="$LABROOT/secure_data"

test -n "$USER" || { echo "Не определено имя пользователя"; exit 1; }
case "$LABROOT" in
  /srv/oslab-lab05-*) ;;
  *) echo "Небезопасное значение LABROOT"; exit 1 ;;
esac

mkdir -p "$EVIDENCE"
printf 'V=%s\nMODE=%s\nACL_PROFILE=%s\nEVENT=%s\n' \
  "$V" "$MODE" "$ACL_PROFILE" "$EVENT" \
  | tee "$EVIDENCE/variant.txt"
```

Зафиксируйте среду:

```bash
{
  date --iso-8601=seconds
  hostnamectl
  uname -a
  ip -brief address
  ip route
} | tee "$EVIDENCE/environment.txt"

dpkg-query -W -f='${binary:Package}\t${Version}\n' \
  coreutils acl aide 2>&1 | tee "$EVIDENCE/packages.txt"
```

### Шаг 2. Создайте учебные учётные записи и группу

Команды идемпотентны: существующие объекты повторно не создаются.

```bash
getent group oslab5 >/dev/null || sudo groupadd oslab5

for account in oslab5_reader oslab5_writer oslab5_auditor; do
  id "$account" >/dev/null 2>&1 \
    || sudo useradd --create-home --shell /usr/sbin/nologin "$account"
done

sudo usermod -aG oslab5 oslab5_writer
getent group oslab5 | tee "$EVIDENCE/group.txt"
for account in oslab5_reader oslab5_writer oslab5_auditor; do
  id "$account"
done | tee "$EVIDENCE/accounts.txt"
```

Если путь `/usr/sbin/nologin` отсутствует, определите доступный путь командой `command -v nologin` и согласуйте замену с преподавателем.

### Шаг 3. Создайте учебное дерево

```bash
sudo mkdir -p "$SECURE"
sudo chown -R "$USER":oslab5 "$LABROOT"

printf 'Открытая учебная запись. Вариант %s.\n' "$V" \
  | tee "$SECURE/public.txt" >/dev/null
printf 'Учебные конфиденциальные данные без реальных секретов.\n' \
  | tee "$SECURE/confidential.txt" >/dev/null
printf 'Опорный файл для контроля удаления.\n' \
  | tee "$SECURE/reference.txt" >/dev/null

chmod "$MODE" "$SECURE"
chmod 640 "$SECURE"/*.txt
chgrp oslab5 "$SECURE"/*.txt

find "$LABROOT" -maxdepth 2 -printf '%M %u %g %p\n' \
  | tee "$EVIDENCE/tree_before.txt"
```

### Шаг 4. Сохраните базовые права до ACL

```bash
{
  ls -ld "$SECURE"
  ls -l "$SECURE"
  stat -c '%A %a %U %G %n' "$SECURE" "$SECURE"/*.txt
} | tee "$EVIDENCE/permissions_before.txt"
```

Письменно спрогнозируйте доступ для владельца, группы `oslab5` и остальных пользователей до применения ACL.

### Шаг 5. Примените ACL своего профиля

Сначала удалите возможные расширенные ACL только с учебного дерева:

```bash
setfacl -Rb "$LABROOT"
```

Для профиля `A1` выполните:

```bash
setfacl -m u:oslab5_reader:r-x "$SECURE"
setfacl -m u:oslab5_reader:r-- "$SECURE"/*.txt
setfacl -m d:u:oslab5_reader:r-x,d:m:r-x "$SECURE"
```

Для профиля `A2` выполните:

```bash
setfacl -m u:oslab5_writer:rwx "$SECURE"
setfacl -m u:oslab5_writer:rw- "$SECURE"/*.txt
setfacl -m d:u:oslab5_writer:rwx,d:m:rwx "$SECURE"
```

Для профиля `A3` сначала задайте широкую именованную запись, затем ограничьте её mask:

```bash
setfacl -m u:oslab5_auditor:rwx "$SECURE"
setfacl -m m:r-x "$SECURE"
setfacl -m u:oslab5_auditor:rw- "$SECURE"/*.txt
setfacl -m m:r-- "$SECURE"/*.txt
setfacl -m d:u:oslab5_auditor:rwx,d:m:r-x "$SECURE"
```

Сохраните результат:

```bash
getfacl -p "$SECURE" "$SECURE"/*.txt \
  | tee "$EVIDENCE/acl_before.txt"

ls -ld "$SECURE" "$SECURE"/*.txt \
  | tee "$EVIDENCE/permissions_after_acl.txt"
```

Объясните знак `+` после прав в выводе `ls -l` и строку `mask` в `getfacl`.

### Шаг 6. Проверьте фактический доступ

Выполните все проверки, даже если конкретная операция должна завершиться отказом:

```bash
{
  echo '=== reader: чтение ==='
  sudo -u oslab5_reader -- cat "$SECURE/public.txt"
  echo "rc=$?"

  echo '=== reader: изменение ==='
  sudo -u oslab5_reader -- sh -c \
    "printf 'reader-test\\n' >> '$SECURE/public.txt'"
  echo "rc=$?"

  echo '=== writer: чтение ==='
  sudo -u oslab5_writer -- cat "$SECURE/public.txt"
  echo "rc=$?"

  echo '=== writer: создание ==='
  sudo -u oslab5_writer -- sh -c \
    "printf 'created by writer\\n' > '$SECURE/writer-created.txt'"
  echo "rc=$?"

  echo '=== auditor: чтение ==='
  sudo -u oslab5_auditor -- cat "$SECURE/public.txt"
  echo "rc=$?"

  echo '=== auditor: изменение ==='
  sudo -u oslab5_auditor -- sh -c \
    "printf 'auditor-test\\n' >> '$SECURE/public.txt'"
  echo "rc=$?"
} 2>&1 | tee "$EVIDENCE/access_tests.txt"
```

Не считайте сообщение `Permission denied` ошибкой выполнения работы, если запрет соответствует вашей политике. Запишите ожидаемый и фактический результат каждой операции.

Если `writer-created.txt` появился, удалите его владельцем до создания эталона:

```bash
rm -f "$SECURE/writer-created.txt"
```

### Шаг 7. Создайте локальную конфигурацию AIDE

Проверьте поддержку AIDE и сохраните версию:

```bash
aide --version | tee "$EVIDENCE/aide_version.txt"
```

Создайте конфигурацию. Переменные должны раскрыться в абсолютные пути:

```bash
cat > "$LAB/aide.conf" <<EOF
database=file:$LAB/aide.db
database_out=file:$LAB/aide.db.new
report_url=stdout

LabRule = p+i+n+u+g+s+m+c+sha256+acl
$LABROOT LabRule
EOF

cp "$LAB/aide.conf" "$EVIDENCE/aide.conf"
aide --config="$LAB/aide.conf" --config-check
```

Если `--config-check` сообщает, что атрибут `acl` не поддерживается данной сборкой AIDE, зафиксируйте сообщение и согласуйте с преподавателем замену строки правила на:

```text
LabRule = p+i+n+u+g+s+m+c+sha256
```

При такой замене изменение ACL может быть замечено косвенно по `ctime`, но полнота контроля ACL будет ниже; это ограничение обязательно указывается в отчёте.

### Шаг 8. Создайте базу доверенного состояния

```bash
aide --config="$LAB/aide.conf" --init \
  2>&1 | tee "$EVIDENCE/aide_init.txt"

test -s "$LAB/aide.db.new"
mv "$LAB/aide.db.new" "$LAB/aide.db"

  2>&1 | tee "$EVIDENCE/aide_baseline_check.txt"

```

До контролируемого события код возврата должен быть `0`. Если это не так, не продолжайте: найдите непредусмотренное изменение или ошибку конфигурации.

### Шаг 9. Выполните событие своего варианта

### Шаг 10. Обнаружьте изменение AIDE

Команда AIDE возвращает ненулевой код, когда находит добавленные, удалённые или изменённые объекты. В данном шаге это ожидаемый результат, а не сбой утилиты.

```bash
set +e
aide --config="$LAB/aide.conf" --check \
  2>&1 | tee "$EVIDENCE/aide_change.txt"
AIDE_RC=${PIPESTATUS[0]}
set -e
printf '%s\n' "$AIDE_RC" | tee "$EVIDENCE/aide_change.rc"
```

Интерпретация младших битов кода возврата AIDE:

- `1` — обнаружены новые файлы;
- `2` — обнаружены удалённые файлы;
- `4` — обнаружены изменённые файлы;
- признаки складываются, поэтому, например, код `3` означает новые и удалённые объекты.

Найдите в отчёте AIDE именно событие своего варианта и укажите, какие атрибуты изменились.

## 11. Типичные ошибки

| Ошибка | Почему это неверно | Как исправить |
|---|---|---|
| `Permission denied` сразу считают сбоем | запрет может быть ожидаемым результатом политики | сравнить операцию с ожидаемыми правами и записать код возврата |
| права файла трактуют как права каталога | `rwx` для каталога имеют другой смысл | отдельно объяснить просмотр списка, создание и проход |
| учитывают именованную ACL, но игнорируют mask | записанные права могут быть неэффективны | анализировать `#effective:` в `getfacl` |
| после ACL ориентируются только на `ls -l` | базовая строка не показывает все записи ACL | сохранять полный вывод `getfacl -p` |
| default ACL считают изменением старых файлов | она наследуется только новыми объектами | проверить ACL нового файла отдельно |
| запускают AIDE на `/` | проверка не укладывается в занятие и затрагивает систему | использовать только правило для `$LABROOT` |
| заменяют `/etc/aide/aide.conf` | изменяется штатная политика ОС | использовать локальный файл `~/oslab/lab05/aide.conf` |
| ненулевой код AIDE считают аварией | коды 1, 2 и 4 обозначают найденные различия | сохранить отчёт и расшифровать битовую сумму |
| обновляют эталон до анализа события | следы изменения теряются | сначала сохранить отчёт, оценить изменение и восстановить объект |
| включают NAT или Bridge ради установки | нарушается изоляция стенда | использовать доверенный локальный репозиторий или обратиться к преподавателю |
| хеши созданы до окончательной правки отчёта | проверка завершается ошибкой | формировать `SHA256SUMS` последним действием |

## 13. Критерии оценивания

| Оценка | Критерии |
|---|---|
| **Отлично** | Стенд и зависимости проверены; базовые права и ACL варианта настроены корректно; mask и эффективные права объяснены; разрешённые и запрещённые операции подтверждены; AIDE обнаружил требуемое событие; доверенное состояние восстановлено; чистая повторная проверка дала код `0`; evidence-комплект целостен; выводы технически обоснованы. |
| **Хорошо** | Основные действия выполнены и событие обнаружено, но есть небольшая неточность в объяснении mask, наследования ACL, атрибутов AIDE или кода возврата; доказательств достаточно. |
| **Удовлетворительно** | Базовые права и ACL настроены частично; получен отчёт AIDE, но проверки доступа, восстановление или анализ выполнены неполно. Границы стенда соблюдены. |
| **Неудовлетворительно** | Нет воспроизводимых доказательств; ACL применена к системным или чужим объектам; изменена штатная конфигурация AIDE; VM подключена к посторонней сети; эталон обновлён до анализа события; работа выполнена вне собственного стенда. |
