# Практическая работа № 16. Итоговое упражнение «красная и синяя команды»

**Дисциплина:** Операционные системы. **Специальность:** 10.05.01 «Компьютерная безопасность», университет, 3-й курс. **Продолжительность:** 90 минут; снимки и проверка стенда выполняются заранее. **Варианты:** 27, номер соответствует номеру студента по списку в журнале.

Тема взята из раздела 4.2 РПД: по сценарию группа Kali выполняет только разрешённые проверки, группа Astra обнаруживает события и усиливает защиту; затем роли меняются, проводится повторная проверка и разбор. Это итоговое упражнение курса: оно собирает навыки инвентаризации сетевой поверхности (ПР7), межсетевого экранирования (ПР8), усиления SSH и конфигураций (ПР12), журналирования и корреляции (ПР10), контроля целостности (ПР13) и реагирования (ПР15) и опирается на лекции 14 «Kali Linux в задачах защитника» и 16 «Реагирование, восстановление и современные тенденции».

**Вариант для предоставленного «Орла» 2.12.22:** Astra Linux Common Edition «Орёл» 2.12.22 на базе Debian 9, Python 3.5. Упражнение готовит скрипт: на Astra разворачивается учебная служба `pr16-svc` с набором слабостей по варианту (в `/srv/pr16`), а на запрос по сети служба отдаёт только факты о своей текущей конфигурации и пишет каждый запрос в журнал. Красная команда (Kali) подключается скриптом `pr16_red.py` и выполняет проверки из опубликованного каталога — по одному безопасному запросу на чтение. Синяя команда (Astra) видит проверки в журнале службы и устраняет слабости, правя учебные файлы конфигурации. Настоящие службы, системный `/var/log` и реальный межсетевой экран не затрагиваются.

**Граница результата:** работа ведётся на собственной Astra с собственной Kali. Красная команда действует строго в рамках каталога разрешённых проверок (правила полигона): только чтение, без подбора паролей, без слепого сканирования портов, по одному соединению на проверку — скрипт ничего вне каталога не делает. Синяя команда правит только учебные объекты в `/srv/pr16`. Набор присутствующих слабостей и целевые значения выбираются при инициализации и до команды reveal не раскрываются; файл `/var/lib/pr16/state.json` до reveal не открывают. Секрет службы — учебная строка; её значение в отчёт не включают.

## 1. Цель и результаты

Цель — провести итоговое упражнение двух команд на одном стенде: красная команда разрешёнными проверками выявляет слабости учебной службы, синяя команда обнаруживает эти проверки по журналу и устраняет слабости, после чего при смене ролей повторная проверка подтверждает результат, и проводится разбор.

Задачи:
- развернуть упражнение и усвоить правила полигона: перечень разрешённых проверок (каталог), что каждая проверяет и почему она безопасна;
- в роли красной команды выполнить каталог проверок против службы и зафиксировать, какие слабости присутствуют (раунд 1, baseline);
- в роли синей команды обнаружить активность красной по журналу службы: источник и перечень проверок;
- устранить присутствующие слабости, приведя конфигурацию, набор правил, список доступа и права секрета к целевому состоянию, и подтвердить это проверкой;
- сменить роли и выполнить повторную проверку (раунд 2, recheck), подтверждающую, что слабости закрыты;
- подготовить отчёт-разбор (сценарий, разведка, обнаружение, усиление, повторная проверка, выводы);
- выполнить самопроверку, итоговую проверку и удалить учебные объекты.

Результат — две разведки красной команды (baseline и recheck), таблица обнаружения синей команды, протокол устранения слабостей, отчёт-разбор, протокол самопроверки (reveal), итоговая проверка (check) и подтверждение удаления. Итог упражнения — не «победа» одной команды, а измеримое улучшение: список слабостей, закрытых между двумя проверками, и доказательство, что активность красной была обнаружена.

## 3. Теория: красная и синяя команды, правила полигона

**Две команды.** В учениях по защите информации красная команда играет нарушителя (наступление), синяя — защитника (оборона и реагирование). Красная ищет и демонстрирует слабости; синяя обнаруживает активность, устраняет слабости и восстанавливает защиту. Смысл не в соперничестве, а в проверке и улучшении защищённости: по итогам у синей команды появляется список подтверждённых недостатков и доказательство, что она способна обнаружить действия нарушителя. В этой работе один стенд проходит оба взгляда: сначала разведка, потом оборона, затем повторная проверка.

**Правила полигона (rules of engagement).** Любая оценка защищённости проводится по согласованным правилам: что разрешено проверять, какими методами, в какое время, что запрещено. Методика NIST SP 800-115 делит оценку на фазы — планирование, проверка, отчётность — и требует заранее задать границы и правила. В этой работе правила заданы жёстко: красная команда выполняет только проверки из опубликованного каталога, каждая из которых безопасна (только чтение, один запрос, без изменения состояния и без подбора паролей). Выход за каталог — нарушение правил полигона. Так учение остаётся управляемым и повторяемым, как и «правила безопасного полигона» из ПР14.

**Каталог проверок и слабости.** Учебная служба `pr16-svc` отдаёт по запросу факт о своей конфигурации, а каждая проверка каталога оценивает один факт как «слабо» или «норма». Слабости соответствуют темам курса:

| Проверка | Что выявляет | Почему это риск |
|---|---|---|
| c1_banner | версия в баннере службы | раскрытие версии помогает подобрать известные уязвимости (минимизация раскрытия, ПР2) |
| c2_anon | анонимный доступ разрешён | доступ без аутентификации (ПР6) |
| c3_tls | передача без шифрования | перехват данных и учётных данных |
| c4_debug | открыт отладочный порт для всех | лишняя сетевая поверхность (ПР7, ПР8) |
| c5_secret | секрет доступен на чтение группе/прочим | слабые права файлов (ПР5) |
| c6_lockout | нет ограничения неуспешных входов | перебор паролей (ПР12, ПР15) |
| c7_admin | админ-порт открыт «from any» | доступ к управлению из любой сети (ПР8) |
| c8_allow | устаревший узел в списке доступа | избыточные доверенные источники |
| c9_errors | подробные сообщения об ошибках | раскрытие путей и внутреннего устройства |

Каталог публикуется полностью; какие слабости действительно присутствуют у вашего варианта, красная команда устанавливает проверками (присутствующие возвращают «слабо», отсутствующие — «норма»).

**Обнаружение (синяя команда).** Каждая проверка красной команды — это сетевое соединение к службе, и служба записывает его в журнал `/srv/pr16/log/service.log`: время, адрес источника, идентификатор проверки. Синяя команда по журналу устанавливает, что проводилась разведка, с какого адреса и какие именно проверки выполнялись. Это прямое приложение журналирования и корреляции из ПР10 и ПР15: активность видна тому, кто смотрит в журналы.

**Усиление (синяя команда).** Устранение слабости — это приведение конфигурации к целевому состоянию: скрыть версию, запретить анонимный доступ, потребовать шифрование, закрыть лишние порты в наборе правил (оставить доступ только из учебной подсети), исправить права секрета, задать ограничение неуспешных входов, убрать устаревший узел, выключить подробные ошибки. Каждое изменение затрагивает только учебные файлы и проверяется скриптом. Принцип — минимизация поверхности и наименьшие привилегии: оставлять открытым и доступным только необходимое.

**Смена ролей и повторная проверка.** После усиления роли меняются, и повторная проверка (recheck) тем же каталогом подтверждает, что ранее найденные слабости закрыты (все проверки возвращают «норма»). Разница между baseline и recheck — измеримый результат упражнения. Повторная проверка после устранения недостатков — обязательный шаг и в ПР7/ПР8, и в методике оценки защищённости.

**Разбор (debrief).** Учение завершается разбором: что нашла красная, что обнаружила и закрыла синяя, что осталось, какие меры применить в реальной системе. В отчёте фиксируют сценарий, разведку, обнаружение, усиление, повторную проверку и выводы — это и есть фаза отчётности методики оценки и «действия после инцидента» из жизненного цикла реагирования.

**Astra Special Edition и современные подходы.** В реальной эксплуатации оценку защищённости проводят аттестованными средствами и по согласованным правилам; в Astra Linux SE защита дополняется мандатным доступом и контролем целостности (лекция 10), а подход zero trust (лекция 16) требует не доверять сети по умолчанию и проверять каждый доступ — что согласуется с минимизацией поверхности и ограничением источников в этой работе.

| c9_errors | Подробные ошибки раскрывают пути | `verbose_errors=yes` |

## 5. Ход выполнения

Упражнению нужны два терминала: на Astra один держит службу (`serve`), второй — для обнаружения и усиления; красная команда работает с Kali (или со второго терминала Astra на её адрес).

### Шаг 1. Развёртывание упражнения и правила полигона — 10 минут

Astra, обычная учебная запись:

```bash
mkdir -p "$HOME/pr16" && cd "$HOME/pr16" || exit
V=1; NN=$(printf %02d "$V"); W="$HOME/pr16"; T="$W/kit/tools/pr16.py"
sudo python3 "$T" init --work "$W" --variant "$V"
python3 "$T" info --work "$W" --field catalog | tee evidence/catalog.txt
PORT=$(python3 "$T" info --work "$W" --field port)
ASTRA_IP=$(python3 "$T" info --work "$W" --field astra)
```

Замените 1 своим вариантом; держите терминал открытым. Ожидание: `init` разворачивает службу `pr16-svc` в `/srv/pr16`, печатает номер упражнения, endpoint, учебные порты и каталог из девяти разрешённых проверок. Изучите таблицы 4 и 5: красная команда выполняет только эти проверки.

### Шаг 2. Раунд 1 — разведка красной команды — 15 минут

Astra: запустите endpoint службы в первом терминале (он слушает заданное время и пишет запросы в журнал):

```bash
sudo python3 "$T" serve --port "$PORT" --seconds 900
```

Kali (или второй терминал Astra), красная команда — только разрешённые проверки:

```bash
cd "$HOME/pr16" || exit
V=1; ASTRA_IP="10.50.$V.10"; PORT=7016; R=kit/tools/pr16_red.py
python3 "$R" scan --host "$ASTRA_IP" --port "$PORT" --round baseline --out findings-baseline.json
```

Если красная работает на Kali, передайте результат на Astra (`scp findings-baseline.json student@$ASTRA_IP:pr16/evidence/`); если на Astra — сохраните сразу в `evidence/` (`--out evidence/findings-baseline.json`). Ожидание: скрипт получает каталог и по каждой проверке печатает `WEAK` или `OK` с фактом. Присутствующие слабости отмечены `WEAK` — это шесть из девяти. Запишите, какие проверки оказались слабыми: их устраняет синяя команда.

### Шаг 3. Раунд 1 — обнаружение синей командой — 15 минут

Astra, второй терминал. Служба записала проверки красной команды в журнал:

```bash
LOG=/srv/pr16/log/service.log
grep ' CHECK ' "$LOG" | awk '{print $2, $4}' | sort | uniq -c | tee evidence/log-checks.txt
```

Составьте таблицу обнаружения `detections.csv` — по строке на каждую проверку, увиденную в журнале, с адресом источника и числом обращений:

```bash
cat > detections.csv <<'EOF'
check,source_ip,count
c1_banner,10.50.1.20,1
c2_anon,10.50.1.20,1
EOF
python3 "$T" detect --work "$W"
```

Добавьте строки по всем проверкам из журнала (красная команда выполняет весь каталог, поэтому обнаруживаются все девять). Ожидание: `detect` проверяет формат и сообщает число источников. В отчёте укажите адрес красной команды и что именно она проверяла.

### Шаг 4. Синяя команда — усиление защиты — 20 минут

Astra, второй терминал. Устраните каждую слабость из найденных красной командой, правя учебные файлы по таблице 5. Примеры (выполняйте только нужные по вашему варианту):

```bash
CONF=/srv/pr16/service.conf; RULES=/srv/pr16/firewall.rules; ALLOW=/srv/pr16/conf/allow.hosts
DBG=$(python3 "$T" info --work "$W" --field debug_port); ADM=$(python3 "$T" info --work "$W" --field admin_port)
sudo sed -i 's/^banner_version=.*/banner_version=off/'   "$CONF"
sudo sed -i 's/^allow_anonymous=.*/allow_anonymous=no/'  "$CONF"
sudo sed -i 's/^require_tls=.*/require_tls=yes/'          "$CONF"
sudo sed -i 's/^login_max_fail=.*/login_max_fail=5/'      "$CONF"
sudo sed -i 's/^verbose_errors=.*/verbose_errors=no/'     "$CONF"
sudo sed -i "s#^allow tcp $DBG from any#allow tcp $DBG from 10.50.$V.0/24#" "$RULES"
sudo sed -i "s#^allow tcp $ADM from any#allow tcp $ADM from 10.50.$V.0/24#" "$RULES"
sudo sed -i "/^203\.0\.113\.$V$/d" "$ALLOW"
sudo chmod 600 /srv/pr16/data/token.secret
sudo python3 "$T" harden-check
```

Устаревший узел берётся из таблицы 3 (столбец «Устаревший узел», `203.0.113.V`). Ожидание: `harden-check` перечисляет присутствующие слабости и их состояние; при полном устранении — «Все слабости варианта устранены». Пока есть строки `СЛАБО`, исправьте соответствующий файл и повторите. Правьте только учебные файлы в `/srv/pr16`.

### Шаг 5. Смена ролей — повторная проверка — 15 минут

Astra: если первый `serve` завершился по времени, запустите его снова, чтобы он отдавал уже исправленную конфигурацию:

```bash
sudo python3 "$T" serve --port "$PORT" --seconds 300
```

Красная команда (смена ролей — проверку выполняет вторая команда) повторяет каталог:

```bash
python3 "$R" scan --host "$ASTRA_IP" --port "$PORT" --round recheck --out findings-recheck.json
```

Сохраните результат в `evidence/` (на Astra — сразу `--out evidence/findings-recheck.json`; с Kali — `scp` в `pr16/evidence/`). Ожидание: все проверки возвращают `OK`, «Слабых проверок: 0». Это подтверждает, что найденные ранее слабости закрыты. Сравните baseline и recheck.

### Шаг 6. Отчёт-разбор — 10 минут

Astra. Напишите `report.md` с разделами (заголовки): «Сценарий», «Разведка», «Обнаружение», «Усиление», «Повторная проверка», «Выводы». Укажите номер упражнения. Проверьте:

```bash
python3 "$T" report --work "$W"
```

Ожидание: все разделы присутствуют, указан `EX-16-NN`, объём 60–1500 слов — «Отчёт принят».

### Шаг 7. Самопроверка, итоговая проверка и удаление — 10 минут

Astra:

```bash
sudo python3 "$T" reveal
sudo python3 "$T" check
sudo python3 "$T" cleanup --yes
sha256sum evidence/* 2>/dev/null > SHA256SUMS.txt
sha256sum session.json detections.csv report.md >> SHA256SUMS.txt
sha256sum -c SHA256SUMS.txt
```

Ожидание: `reveal` раскрывает набор присутствовавших слабостей и сверяет его с baseline красной команды и с итоговым состоянием (что нашла, что закрыто). `check` — все строки OK и `passed: True`: есть обе разведки, красная нашла все присутствующие слабости, таблица обнаружения соответствует журналу, все слабости устранены, повторная проверка их не показывает, отчёт принят, самопроверка выполнена. `cleanup` удаляет `/srv/pr16` и `/var/lib/pr16` и печатает `"clean": true`. Доказательства в рабочем каталоге остаются.
