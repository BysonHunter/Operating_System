# Практическая работа № 13. Обнаружение изменения критичных файлов

**Дисциплина:** Операционные системы. **Специальность:** 10.05.01 «Компьютерная безопасность», университет, 3-й курс. **Продолжительность:** 90 минут; установка пакетов и снимки выполняются заранее. **Варианты:** 27, номер соответствует номеру студента по списку в журнале.

Тема взята из раздела 4.2 РПД: создание эталона целостности, внесение заранее разрешённого изменения в тестовый файл, обнаружение события и восстановление доверенной версии. Работа опирается на лекцию 13 «Журналирование, аудит и контроль целостности» и продолжает ПР5. В ПР5 AIDE контролировал один учебный каталог, а эталон лежал на той же машине. Здесь объект контроля похож на настоящую систему: пакетные файлы службы, её конфигурация, данные вне пакета, растущий журнал и временные файлы. Эталон хранится вне контролируемого узла — на Kali.

**Вариант для предоставленного «Орла» 2.12.22:** Astra Linux Common Edition «Орёл» 2.12.22 на базе Debian 9: dpkg 1.18, Python 3.5, AIDE из пакета выпуска (для Debian 9 — 0.16). Kali — хранилище эталона из стенда ПР1 с OpenSSH-клиентом. Учебные объекты создаёт скрипт: пакет `pr13-agent` с файлами в `/usr/lib/pr13-agent` и `/etc/pr13-agent`, каталог `/srv/pr13`. Системные критичные файлы варианта только читаются. Синтаксис конфигурации подходит и для AIDE 0.16, и для новых версий: команда шага 2 сама выбирает имя параметра `database` или `database_in`.

**Граница результата:** работа проверяет собственную Astra с собственной Kali. Все изменения затрагивают только учебные объекты. Шаг 4 имитирует действия нарушителя: скрипт вносит одно-два неразрешённых изменения в учебные файлы и, как это сделал бы нарушитель с правами root, перестраивает локальную базу AIDE. Что именно изменено, скрипт не сообщает — это нужно установить самостоятельно; служебный файл `/var/lib/pr13/state.json` до команды reveal не открывается. Пароли, парольная фраза и закрытый ключ в отчёт не включаются.

## 1. Цель и результаты

Цель — построить контроль целостности для объектов разных категорий, вынести эталон за пределы контролируемого узла, отличить разрешённое изменение от неразрешённого и восстановить доверенные версии из доверенных источников, после чего обновить эталон.

Задачи:
- составить политику AIDE с разными наборами атрибутов для исполняемых файлов, конфигурации, растущего журнала и временных файлов и проверить её скриптом;
- создать эталон, проверить его, выгрузить и сохранить на Kali с контрольной суммой манифеста;
- внести изменение строго по заявке варианта;
- после учебного события обнаружить, что локальная проверка ничего не показывает, сравнить эталон с копией на Kali и выполнить проверку по доверенному эталону;
- сопоставить отчёт AIDE и `dpkg --verify`, классифицировать каждое отличие;
- восстановить неразрешённые изменения из доверенного пакета и резервной копии, полученных с Kali, поместить неожиданный файл в карантин;
- создать новый эталон с учётом заявки, сохранить его на Kali, подтвердить итоговое состояние и удалить учебные объекты.

Результат — политика AIDE и протокол её проверки, три выгрузки эталона, журнал хранилища Kali, отчёты AIDE (локальный после события, по доверенному эталону до и после восстановления, итоговый), вывод `dpkg --verify`, таблица классификации, протокол самопроверки, контрольная проверка итогового состояния и подтверждение удаления. Не объявляйте систему чистой по одной локальной проверке: в этой работе она заведомо обманута.

## 3. Теория: эталон, атрибуты и доверенные копии

**Эталон.** Контроль целостности сравнивает текущее состояние объектов с сохранённым доверенным состоянием — эталоном. AIDE записывает в базу атрибуты каждого объекта: права (p), индексный дескриптор (i), число ссылок (n), владельца и группу (u, g), размер (s), время изменения содержимого mtime (m), время изменения метаданных ctime (c) и хеши содержимого (sha256, sha512). При проверке атрибуты вычисляются заново. Код возврата `aide --check` складывается из признаков: 1 — новые объекты, 2 — удалённые, 4 — изменённые; 0 — отличий нет.

**Атрибуты зависят от категории.** Исполняемые файлы и библиотеки в норме не меняются, для них проверяется всё. Конфигурация меняется только по заявке, для неё обязательны хеш, права и владелец. Журнал растёт постоянно: хеш, размер, mtime и ctime у него меняются при каждой записи. Поэтому для журнала проверяют только права, владельца и группу (и, если нужно, inode), иначе каждая проверка даст ложное срабатывание. Временные файлы и кэши исключают отрицательным правилом `!путь`.

**Почему mtime недостаточно.** Команда `touch -r` или системный вызов utime возвращают файлу прежнее время изменения. Если подменённое содержимое имеет тот же размер, размер и mtime ничего не покажут. Подмену выдаст хеш. ctime при этом изменится: обычными средствами его не вернуть назад без перевода системных часов. Поэтому в отчёте о такой подмене виден изменённый хеш и ctime при неизменных размере и mtime.

**Где хранится эталон.** Нарушитель с правами root на узле может не только изменить файл, но и перестроить базу AIDE, после чего локальная проверка покажет отсутствие отличий. Защита — хранить эталон вне контролируемого узла и перед проверкой убеждаться, что база совпадает с доверенной копией. В работе доверенное хранилище — Kali: эталон переносится туда сразу после создания, копии становятся доступны только для чтения, а для манифеста выгрузки вычисляется SHA256. Тот же манифест сверяется на Astra перед использованием присланных копий.

**dpkg --verify и AIDE.** dpkg хранит контрольные суммы MD5 файлов пакета и сумму конфигурационных файлов. `dpkg --verify` сравнивает с ними установленные файлы: строка `??5?????? c /etc/…` означает, что изменилось содержимое конфигурационного файла (c — conffile), `??5??????   /usr/…` — содержимое обычного файла пакета. dpkg 1.18 проверяет только содержимое: изменение прав или владельца и появление новых файлов он не показывает. Его база лежит на той же машине, а MD5 устарел как криптографическая функция. Поэтому `dpkg --verify` — быстрый второй взгляд, но не замена эталону.

**Разрешённое и неразрешённое.** Сообщение AIDE не доказывает атаку: оно показывает отличие от эталона. Каждое отличие сопоставляют с заявкой на изменение. Совпадающее с заявкой — разрешённое; не предусмотренное заявкой — неразрешённое и требует восстановления и разбора; объяснимое штатной работой (например, рост журнала, изменение каталога после создания или удаления файла в нём) — нормальная активность, но её объяснение тоже записывают.

**Восстановление доверенной версии.** Источник восстановления должен быть доверенным, иначе можно «восстановить» подменённый файл. Файл пакета точечно извлекают из доверенного пакета: `dpkg-deb --fsys-tarfile` выдаёт архив файлов пакета, из которого tar извлекает нужный путь с правами. Повторная установка всего пакета тоже возможна, но заменит и неизменённые файлы. Файл вне пакета берут из резервной копии. Неожиданный новый файл не удаляют сразу: сначала записывают его хеш и перемещают в карантин для разбора. Восстановленный файл совпадает с эталоном по содержимому, правам и mtime, но это новый индексный дескриптор с новым ctime, а каталог, где он лежит, тоже меняет mtime и ctime. Поэтому эталон обновляют только после восстановления и повторной проверки.

**Обновление эталона.** Разрешённое изменение остаётся в системе, значит, старый эталон устарел. Новый эталон создают после устранения всех неразрешённых изменений и сохраняют в доверенном хранилище под новой меткой, связанной с заявкой. Старый эталон не удаляют: он нужен для разбора.

**Astra Special Edition.** В Astra Linux SE есть собственные средства регламентного контроля целостности в составе КСЗ (лекция 10). В «Орле» и в этой работе используется AIDE, как в ПР5; принципы эталона и его защиты те же.

```bash

/srv/pr13/policy CONF
```

Таблица 6 — Оценивание

| Оценка | Критерии |
|---|---|
| 5 | Политика принята скриптом, атрибуты обоснованы; эталон проверен и сохранён на Kali со сверкой ключа узла и манифеста; заявка выполнена точно; ложная локальная проверка распознана и объяснена; проверка по доверенному эталону и `dpkg --verify` сопоставлены; все отличия классифицированы верно (reveal без расхождений или расхождения разобраны); восстановление из доверенных копий подтверждено повторной проверкой; новый эталон сохранён; итоговая проверка и удаление чистые; ответы полны |
| 4 | Основной сценарий выполнен и подтверждён; одна неточность классификации или пробелы в объяснениях атрибутов не меняют выводов |
| 3 | Изменения обнаружены и восстановлены, но часть доказательств неполна (нет сверки манифеста, сопоставления с dpkg или повторной проверки); недочёты исправляются с преподавателем |
| 2 | Вывод о чистоте системы сделан по локальной проверке; восстановление выполнено из недоверенного источника или не подтверждено; эталон обновлён до устранения неразрешённых изменений; результаты не подтверждены |

Критические нарушения: чтение `/var/lib/pr13/state.json` до reveal; изменение системных критичных файлов или объектов вне учебных путей; выполнение изменений сверх заявки; использование присланных копий без сверки манифеста; принятие ключа узла без сверки при несовпадении отпечатка; отключение проверки подписей APT или подключение случайных репозиториев; публикация паролей, парольной фразы или закрытого ключа; вымышленные результаты.

## 8. Диагностика и источники

Таблица 7 — Типовые затруднения

| Симптом | Проверить и сделать |
|---|---|
| init: нет программы aide | Раздел 2.2; не продолжайте без AIDE |
| init: объекты ПР13 уже существуют | Повторный запуск: верните снимок или `sudo python3 "$T" cleanup --yes` |
| dpkg -i отказывает при init | Сообщение dpkg; в «Орле» CE контроль подписи пакетов не включён; в SE с ЗПС обратитесь к преподавателю |
| policy-check: config-check FAIL | Сообщение AIDE; имя параметра базы для вашей версии (`database` или `database_in`); опечатка в группе |
| policy-check: LOG — лишние атрибуты | Для журнала только p, u, g (i, n допустимы); уберите s, m, c и хеши |
| policy-check: EXCL покрыто | Отрицательное правило `!/srv/pr13/tmp` отсутствует или слишком широкое правило захватило каталог |
| `aide --check` после init даёт не 0 | Объект менялся между init и check; посмотрите отчёт, повторите init |
| trust: ключ ed25519 не получен | Служба ssh, адрес, маршрут, политика ПР8 |
| ssh-copy-id: Permission denied | Пароль учебной записи; PasswordAuthentication в конфигурации после ПР12 |
| store/compare: Connection closed, subsystem request failed | Нет SFTP на сервере: добавьте `--scp-legacy` в VT |
| Host key verification failed | known_hosts не соответствует узлу; остановитесь и выясните причину |
| drill: файл не соответствует заявке | Сравните agent.conf с заявкой: изменён только параметр варианта, без лишних пробелов |
| stage: ОТКАЗ, SHA256 манифеста не совпадает | Ошибка ввода или подмена копий; повторите push на Kali, сверьте значение |
| Проверка по доверенному эталону даёт 0 | Конфигурация aide-trusted.conf указывает не на `/var/lib/pr13/trusted/aide.db`; проверьте строку database |
| tar: Not found in archive | Путь в архиве: `./usr/...` для пакета, `srv/pr13/...` для резервной копии; сверьте со списком `tar -tvf` |
| clean-check: dpkg --verify FAIL | Остался неразрешённый файл пакета или изменено больше, чем заявка |
| clean-check: kali vault FAIL | На Kali не выполнены store с новой меткой и report |
