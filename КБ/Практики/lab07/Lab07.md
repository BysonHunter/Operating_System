## 1. Цель, задачи и результаты

Цель — определить сетевую поверхность собственной Astra Linux с позиции внешнего наблюдателя Kali Linux и объяснить обнаруженные порты через локальные сокеты, процессы, пользователей и службы.

Задачи:

1. Проверить изоляцию и исходное состояние стенда.
2. Получить локальный перечень TCP- и UDP-сокетов Astra Linux.
3. Выполнить ограниченное TCP-сканирование единственного разрешённого адреса.
4. Сопоставить результаты сканирования с PID, владельцами и unit systemd.
5. Сравнить два временных HTTP-сервиса с разными адресами привязки.
6. Подготовить обоснованный перечень кандидатов на уменьшение поверхности атаки и восстановить исходное состояние.

Результат — таблица сопоставления портов и процессов, доказательства состояний до/во время/после эксперимента, перечень необходимых и потенциально избыточных сервисов. Наличие открытого порта само по себе не доказывает уязвимость.

### 2.3. Границы разрешённых действий

- Сканируется только один IPv4 собственной Astra из паспорта. Подсети, диапазоны адресов, хост и чужие VM не сканируются.
- Разрешён Nmap TCP connect scan `-sT`, без `sudo`, с командами этой работы. UDP изучается локально через `ss`, без UDP-сканирования.
- Не применяйте `-A`, `-sV`, NSE-скрипты, перебор паролей, эксплуатацию, обход фильтров, скрытие следов или нагрузочные испытания.
- Не меняйте firewall, PAM, SSH, штатные службы, мандатные механизмы Astra и настройки сети.
- Временные HTTP-сервисы запускаются обычным пользователем, только на двух портах варианта и только из каталога искусственных данных.
- При выходе за границы стенда немедленно прекратите работу и сообщите преподавателю. Секреты и реальные персональные данные в доказательства не включаются.

## 3. Необходимая теория

Сетевой endpoint описывается протоколом, адресом и портом. TCP-сокет в состоянии LISTEN означает, что приложение ожидает соединения. UDP не устанавливает TCP-подобного соединения: его локальные сокеты также нужно учитывать, но результат TCP-сканирования ничего не говорит о доступности UDP.

Привязка к `127.0.0.1` разрешает прямой доступ только с самой Astra. Привязка к адресу `10.50.V.10` создаёт точку входа через учебный интерфейс. `0.0.0.0` означает все локальные IPv4-интерфейсы. IPv6-сокет `[::]` анализируйте отдельно: поведение IPv4 зависит от настройки двойного стека. В работе проверяется удалённая доступность только IPv4 TCP.

Nmap с `-sT` использует системный вызов `connect()`. `open` означает, что TCP-соединение возможно; `closed` — получен ответ, указывающий на отсутствие принимающего сервиса на проверяемом endpoint; `filtered` — по ответам или их отсутствию состояние определить нельзя. Фильтрация не доказывает отсутствие процесса. Колонка SERVICE без определения версии — справочная метка по номеру порта, а не подтверждение реально запущенного приложения.

Локальный и удалённый наблюдатели видят разные стороны системы. Сокет может слушать loopback, конкретный интерфейс или быть недоступным из-за фильтрации. Поэтому сопоставляйте цепочку:

```text
IPv4:TCP-порт → bind-адрес → PID → команда → пользователь → unit/сеанс → назначение
```

Не каждый процесс является systemd-службой: временный сервер этой работы запускается из пользовательского терминала. systemd также может активировать службу через socket-unit; смотрите и службы, и сокеты. Порт считается избыточным по назначению узла, а не по «подозрительному» номеру. Неизвестный сервис требует уточнения, а не немедленного отключения.

Связанная теория: [лекция 11 общего конспекта](../../Лекции/OS-lecture-notes.md#лекция-11-службы-сеть-и-безопасная-конфигурация-ос).

## 6. Ход выполнения

### 6.1. Проверить стенд и задать параметры

На обеих VM откройте Bash под обычным учебным пользователем. В основном терминале каждой VM выполните, заменив `1` своим номером:

```bash
V=1
if ! [[ "$V" =~ ^([1-9]|1[0-9]|2[0-7])$ ]]; then
  printf 'Номер варианта должен быть целым числом от 1 до 27.\n' >&2
else
ASTRA_IP="10.50.${V}.10"
KALI_IP="10.50.${V}.20"
P=$((18000 + V))
Q=$((19000 + V))
R=$((20000 + V))
mkdir -p ~/oslab/lab07/evidence
cd ~/oslab/lab07
date -Is | tee evidence/start-time.txt
ip -br -4 address | tee evidence/addresses.txt
ip -4 route | tee evidence/routes.txt
printf 'V=%s Astra=%s Kali=%s P=%s Q=%s R=%s\n' \
  "$V" "$ASTRA_IP" "$KALI_IP" "$P" "$Q" "$R" | tee evidence/parameters.txt
fi
```

Если проверка номера выдала ошибку, исправьте V и повторите блок; к следующим командам не переходите. Проверьте параметры по паспорту и отсутствие default route. Если адреса отличаются от типового профиля, задайте фактические ASTRA_IP и KALI_IP в обоих основных терминалах и заново сохраните `evidence/parameters.txt`. Изменение переменной в одном терминале не переносится в остальные терминалы. Если найдены дополнительный адаптер, внешний маршрут или неверный адрес, остановитесь до исправления стенда. В гипервизоре создайте снимок Astra `pre-lab07-VNN`. Сохраните версии инструментов из раздела 2 в отчёт.

На Kali проверьте маршрут к единственной цели:

```bash
ip -4 route get "$ASTRA_IP" | tee evidence/target-route.txt
ping -c 2 -W 2 "$ASTRA_IP" | tee evidence/ping.txt
```

Маршрут должен идти через учебный интерфейс с исходным адресом Kali из паспорта. Отсутствие ответа ping не доказывает выключенную VM: ICMP может фильтроваться. Проверьте консоль Astra и адреса; защиту не отключайте.

### 6.2. Собрать локальную инвентаризацию

В основном терминале Astra, каталог `~/oslab/lab07`; `sudo` нужен только для чтения сведений о процессах:

```bash
sudo ss -lntp | tee evidence/tcp-before.txt
sudo ss -lnup | tee evidence/udp-before.txt
systemctl list-units --type=service --state=running --no-pager \
  | tee evidence/services-before.txt
systemctl list-sockets --all --no-pager | tee evidence/socket-units.txt
sudo ss -lntp "( sport = :$P or sport = :$Q or sport = :$R )" \
  | tee evidence/variant-ports-before.txt
```

Ожидание для последней команды: заголовок без строк сокетов. Иначе порт занят — действуйте по разделу 4. Из общего списка отдельно выпишите сетевые IPv4-слушатели и loopback. Сведения о UDP и IPv6 сохраните как локальную инвентаризацию; удалённо в этой работе они не проверяются.

### 6.3. Выполнить исходное сканирование

В основном терминале Kali, без `sudo`:

```bash
nmap -sT -Pn -n --top-ports 1000 -T3 --max-rate 30 \
  --max-retries 2 --host-timeout 180s --reason \
  -oA evidence/baseline-top1000 "$ASTRA_IP"
```

`-Pn` пропускает предварительную проверку доступности; это не доказательство, что цель отвечает. `-n` отключает DNS-запросы; `--top-ports 1000` выбирает 1000 наиболее распространённых TCP-портов по базе установленного Nmap. `-T3`, предел скорости и числа повторов ограничивают темп; `--host-timeout` ограничивает время. `--reason` сохраняет причину состояния, `-oA` — текстовый, XML и grepable-файлы. Это выборочная проверка, а не полный перечень всех 65535 портов.

Если сработал `--host-timeout`, Nmap может не вывести таблицу портов для этой цели. Сохраните сообщение о тайм-ауте; отсутствие таблицы не означает отсутствие открытых портов. Не записывайте состояния непроверенных портов. Продолжите адресную проверку ниже. Не повышайте скорость и не делайте вывод о непроверенных портах. Не используйте `--open`: закрытые и фильтруемые порты нужны для сравнения.

Задайте фиксированную область сравнения, включив P, Q, R, распространённые порты и фактически найденные на Astra IPv4 TCP-слушатели. Дополнительные номера введите вручную через запятую; если их нет, оставьте пустую строку. При более чем 32 дополнительных портах согласуйте набор с преподавателем.

```bash
EXTRA=''  # например, '5432,8443', только из локального ss на Astra
PORTS="22,80,443,445,631,3389,8080,$P,$Q,$R"
if [ -n "$EXTRA" ]; then PORTS="$PORTS,$EXTRA"; fi
printf '%s\n' "$PORTS" | tee evidence/scan-ports.txt
nmap -sT -Pn -n -p "$PORTS" -T3 --max-rate 30 \
  --max-retries 2 --host-timeout 120s --reason \
  -oA evidence/before "$ASTRA_IP"
```

Для каждого сканирования проверьте, что в сохранённом `.nmap` есть таблица портов цели, а не только сообщение о тайм-ауте. Если адресная проверка также не завершилась, сохраните её файлы и повторите команду только с `-p "$P,$Q,$R"`, сохраняя прежние ограничения и отдельный префикс вывода, например `-oA evidence/before-PQR`. Полный набор PORTS не меняйте: остальные порты отметьте как непроверенные. Это правило действует и для проверок во время и после эксперимента; соответствующие префиксы — `during-PQR` и `after-PQR`. Если даже проверка P/Q/R не завершилась, остановите опыт и разберите маршрут и сообщения с преподавателем.

Ожидание для завершённого сканирования: для P, Q, R нет `open`; возможны `closed` или `filtered`. Если получен `open`, повторите локальную проверку и выясните источник до запуска серверов. Сохраните один и тот же PORTS для всех следующих сравнений.

### 6.4. Запустить два временных HTTP-сервиса

В основном терминале Astra создайте отдельные каталоги с искусственными данными:

```bash
mkdir -p public local
printf 'lab07 V=%s endpoint=network\n' "$V" > public/index.html
printf 'lab07 V=%s endpoint=loopback\n' "$V" > local/index.html
```

Откройте два дополнительных терминала Astra под тем же обычным пользователем. В каждом снова задайте V своим номером и убедитесь, что это число от 1 до 27. В терминале A отдельно задайте **фактический** ASTRA_IP из проверенных параметров основного терминала; ниже адрес дан как пример для варианта 1. Если преподаватель заменил занятые порты P/Q, в этих терминалах используйте подтверждённые номера вместо вычисляемых значений. **Терминал A**:

```bash
V=1
ASTRA_IP='10.50.1.10'  # заменить фактическим IPv4 своей Astra
P=$((18000 + V))
cd ~/oslab/lab07/public
python3 -u -m http.server "$P" --bind "$ASTRA_IP" 2>&1 \
  | tee ../evidence/server-network.log
```

**Терминал B**:

```bash
V=1
Q=$((19000 + V))
cd ~/oslab/lab07/local
python3 -u -m http.server "$Q" --bind 127.0.0.1 2>&1 \
  | tee ../evidence/server-loopback.log
```

Ожидание: сообщение о прослушивании заданного адреса и порта, процесс работает в переднем плане. `-u` отключает буферизацию вывода Python; `tee` показывает сообщения и одновременно сохраняет их в файле доказательств. После остановки серверов убедитесь, что соответствующие файлы содержат сообщения запуска и достигших сервера запросов. Не запускайте сервер из домашнего или системного каталога: HTTP-сервер может отдавать файлы своего рабочего каталога. На R ничего не запускайте.

В основном терминале Astra:

```bash
sudo ss -lntp "( sport = :$P or sport = :$Q or sport = :$R )" \
  | tee evidence/variant-ports-during.txt
curl --noproxy '*' --connect-timeout 3 --max-time 5 \
  "http://$ASTRA_IP:$P/" > evidence/http-network-local.txt 2>&1
printf 'curl_exit=%s\n' "$?" >> evidence/http-network-local.txt
curl --noproxy '*' --connect-timeout 3 --max-time 5 \
  "http://127.0.0.1:$Q/" > evidence/http-loopback-local.txt 2>&1
printf 'curl_exit=%s\n' "$?" >> evidence/http-loopback-local.txt
cat evidence/http-network-local.txt evidence/http-loopback-local.txt
```

Ожидание: два TCP-слушателя с разными bind-адресами и PID; обе локальные HTTP-проверки возвращают соответствующую строку страницы и код 0. Если это не так, сначала исправьте запуск учебных процессов. `--noproxy '*'` исключает использование настроенного HTTP-прокси.

### 6.5. Проверить удалённую доступность с Kali

В основном терминале Kali с прежними ASTRA_IP и PORTS:

```bash
nmap -sT -Pn -n -p "$PORTS" -T3 --max-rate 30 \
  --max-retries 2 --host-timeout 120s --reason \
  -oA evidence/during "$ASTRA_IP"
curl --noproxy '*' --connect-timeout 3 --max-time 5 \
  "http://$ASTRA_IP:$P/" > evidence/http-P.txt 2>&1
printf 'curl_exit=%s\n' "$?" >> evidence/http-P.txt
curl --noproxy '*' --connect-timeout 3 --max-time 5 \
  "http://$ASTRA_IP:$Q/" > evidence/http-Q.txt 2>&1
printf 'curl_exit=%s\n' "$?" >> evidence/http-Q.txt
cat evidence/http-P.txt evidence/http-Q.txt
```

Если действующая защита допускает соединение, P будет `open`, а HTTP вернёт страницу `endpoint=network`. Q не должен быть `open`: сервер слушает только `127.0.0.1` Astra. R по-прежнему без слушателя. При фильтрации P удалённый запрос может завершиться ошибкой: сохраните результат, локальный успех, bind-адрес и причину Nmap. Это корректный результат наблюдения; firewall не меняйте. Тайм-аут совместим с фильтрацией или проблемой пути и сам по себе не устанавливает конкретное правило firewall.

Если Q оказался `open`, проверьте наличие другого процесса на сетевом адресе, правильность цели и выбранного порта. Не выдавайте доступ к другому сервису за доступ к loopback-серверу.

### 6.6. Сопоставить порты с процессами и службами

На Astra сохраните полный список во время эксперимента:

```bash
sudo ss -lntp | tee evidence/tcp-during.txt
```

Для каждого обнаруженного открытого порта и обоих учебных серверов найдите PID в `ss`. Подставьте фактический PID вместо примера:

```bash
PID=1234  # заменить числом из ss
ps -p "$PID" -o pid,ppid,user,comm,args
systemctl status "$PID" --no-pager
```

Сохраните вывод в отдельный файл для каждого PID, например:

```bash
ps -p "$PID" -o pid,ppid,user,comm,args > "evidence/process-$PID.txt"
systemctl status "$PID" --no-pager > "evidence/unit-$PID.txt" 2>&1
```

Если systemctl не находит unit, сохранённое сообщение является результатом проверки, а не поводом останавливать опыт. Для штатной службы изучите её фактический unit: `systemctl show ИМЯ.service -p MainPID -p User -p ExecStart` и `systemctl status ИМЯ.service --no-pager`. Поле User может быть пустым; владельца работающего процесса определяйте по `ps`. Учебные серверы могут относиться к пользовательскому сеансу/scope, а не к отдельной service-unit. Если unit не найден, зафиксируйте это, не придумывая имя.

Сопоставьте все открытые порты в области сканирования с локальными сведениями. Отдельно объясните минимум три контрольных порта P/Q/R и все локальные IPv4-слушатели, отсутствующие среди удалённых открытых портов. Если PID скрыт политикой Astra, используйте разрешённый `sudo`; при сохранении ограничения обратитесь к преподавателю, защиту не ослабляйте.

Для штатных сервисов запишите фактическое назначение и одну из категорий: «необходим», «кандидат на ограничение/отключение», «назначение требует уточнения». Если роль узла не позволяет решить, укажите, какие сведения нужны. Учебные серверы после опыта однозначно избыточны. Штатные сервисы в этой работе не отключайте.

## 10. Типовые ошибки

Таблица 6 — Диагностика

| Симптом | Проверить | Действие |
|---|---|---|
| `Address already in use` | Локальный `ss`, адрес и порт | Не завершать чужой процесс; выбрать свободный порт с преподавателем и зафиксировать замену |
| `Cannot assign requested address` | V, адрес Astra, интерфейс | Исправить параметр по паспорту; не менять сеть автоматически |
| HTTP не отвечает даже локально | Терминал сервера, bind-адрес, `ss`, ошибка Python | Исправить запуск своего процесса; не менять firewall |
| P локально работает, с Kali недоступен | Маршрут, цель, состояние Nmap, bind-адрес | Зафиксировать различие; для чтения правил защиты обратиться к преподавателю |
| В ss нет PID | Права и политика Astra | Разрешённое чтение через sudo; при ограничении обратиться к преподавателю |
| Nmap завершился по тайм-ауту | Размер области, сетевой путь, сообщения | Сохранить неполный результат; использовать ограниченную адресную проверку |
| Результаты другого варианта | V в каждом терминале, фактические адреса/порты | Исправить собственные параметры и повторить соответствующие измерения |
| SERVICE не совпадает с процессом | Справочная база Nmap и локальный PID | Доверять подтверждённой цепочке сокет → процесс, отметить различие |
| После Ctrl+C порт остался open | Локальный PID и повторный запуск | Найти именно свой сервер; штатные процессы не завершать |
