## 1. Цель и задачи

Цель — настроить дополнительную политику входящего IPv4-трафика учебного интерфейса Astra и доказать действие фильтрации при продолжающейся работе служб.

Задачи: проверить стенд и средства; получить исходные ответы двух HTTP-служб и одной UDP-службы; составить политику варианта; проверить её без применения; назначить автоматический откат; подключить собственную цепочку; повторить ограниченные сетевые проверки; сопоставить ответы со слушающими сокетами и счётчиками; удалить собственные изменения и доказать восстановление.

Результат — обоснованная цепочка «требование → правило → проверка → наблюдение → вывод». Недоступность порта сама по себе не доказывает остановку процесса или устранение уязвимости.

## 3. Подготовка и восстановление сети

### 3.1. Версии и недостающие программы

На каждой VM, Bash, обычный пользователь, домашний каталог:

```bash
mkdir -p "$HOME/pr8/results"
cd "$HOME/pr8" || exit
cat /etc/os-release | tee results/os-release.txt
uname -r | tee results/kernel.txt
dpkg --print-architecture | tee results/architecture.txt
python3 --version
ip -4 address show
ip -4 route
ip -6 route
```

При повторном выполнении заранее сохраните прежние результаты под другим именем. На Astra:

```bash
for c in iptables iptables-save iptables-restore ip6tables-save modinfo modprobe ip ss python3 curl ping systemctl systemd-run journalctl sudo install sha256sum; do
    command -v "$c" || printf 'ОТСУТСТВУЕТ: %s\n' "$c"
done
iptables --version
systemctl --version
```

На Kali:

```bash
for c in nmap curl python3 ip ping sudo sha256sum; do
    command -v "$c" || printf 'ОТСУТСТВУЕТ: %s\n' "$c"
done
nmap --version
```

Ожидание: пути ко всем командам и версии. На Astra из данного ISO ожидается iptables 1.6.0 и Python 3.5.3. Если VM показывает иной backend/выпуск, не переключайте его автоматически; согласуйте образ с преподавателем. Наличие пакета на ISO не означает его установку в VM. При отсутствии sudo установка выполняется преподавателем через консоль root, без самостоятельного изменения прав учебной записи.

### 3.2. Установка с временным NAT или с носителя

Сохраните настройки из паспорта и скриншоты обеих VM. Выключите нужную VM, переключите **тот же единственный адаптер** на NAT. После запуска в штатном графическом менеджере её проводного подключения выберите IPv4 «Автоматически (DHCP)» и автоматические DNS, примените и переподключитесь. Проверьте получение адреса и маршрута командами `ip -4 address show` и `ip -4 route`. Не добавляйте второй адаптер, не используйте Bridged. Пока включён NAT, сканирование и учебные службы не запускаются.

На каждой VM проверьте собственные источники APT: `/etc/apt/sources.list` и файлы `.list`/`.sources` в `/etc/apt/sources.list.d`. Не смешивайте Astra, Debian, Kali и разные выпуски Astra. В терминале Astra, каталог `$HOME/pr8`, команды установки через sudo:

```bash
sudo apt-get update
apt-cache policy iptables kmod python3 iproute2 curl iputils-ping systemd
sudo apt-get -s install iptables kmod python3 iproute2 curl iputils-ping systemd sudo coreutils bash
sudo apt-get install iptables kmod python3 iproute2 curl iputils-ping systemd sudo coreutils bash
```

На Kali:

```bash
sudo apt-get update
apt-cache policy nmap curl python3 iproute2 iputils-ping
sudo apt-get -s install nmap curl python3 iproute2 iputils-ping sudo coreutils bash
sudo apt-get install nmap curl python3 iproute2 iputils-ping sudo coreutils bash
```

Каждую команду установки выполняйте после успешной предыдущей. Изучите пробную установку `-s`: не продолжайте, если предлагается удалить защиту или изменить выпуск ОС. При необходимости установите `unzip` отдельно. APT разрешает зависимости. Полное обновление ОС не требуется; проверку подписей не отключайте.

Если старый сетевой репозиторий недоступен, используйте установочный/репозиторный ISO **того же выпуска и архитектуры**. Подключите его к DVD VM; в консоли Astra преподаватель регистрирует диск командой `sudo apt-cdrom add`, после чего выполняет установку перечисленных пакетов через apt-get. При запросе используйте этот же диск. Действующий firewall ради APT не отключайте. Для Kali нужны собственный репозиторий/носитель и зависимости. Если полного комплекта нет, используйте подготовленный преподавателем образ или локальный репозиторий идентичного выпуска; не переносите отдельные DEB из случайных дистрибутивов.

### 3.3. Проверка модулей Astra

В консоли Astra, из `$HOME/pr8`, обычный пользователь:

```bash
for module in ip_tables iptable_filter nf_conntrack nf_conntrack_ipv4 xt_conntrack xt_comment xt_tcpudp; do
    modinfo "$module"
done
```

Указанные модули присутствуют в пакетах generic и hardened ядра 4.15.3-1 данного ISO. `modinfo` описывает файл модуля, но не подтверждает его загрузку. На Astra с этим ядром преподаватель/пользователь с sudo выполняет:

```bash
sudo modprobe iptable_filter
sudo modprobe nf_conntrack_ipv4
sudo modprobe xt_conntrack
sudo modprobe xt_comment
sudo modprobe xt_tcpudp
sudo iptables -t filter -S | tee results/filter-ready.txt
```

Ожидание: загрузка без ошибок и чтение filter без ошибки прав/ядра. Загрузка перечисленных модулей не создаёт учебных правил. Если `modinfo` пишет, что модуль не найден, сверяйте `uname -r` и `/lib/modules/$(uname -r)`. Для ядра данного образа файлы входят в соответствующий пакет `linux-image-4.15.3-1-generic` или `linux-image-4.15.3-1-hardened`; установите/переустановите **пакет именно работающего ядра** из совместимого источника. Например, только при совпадении ядра и доступном кандидате:

```bash
apt-cache policy "linux-image-$(uname -r)"
sudo apt-get -s --reinstall install "linux-image-$(uname -r)"
sudo apt-get --reinstall install "linux-image-$(uname -r)"
sudo depmod -a
```

Повторите проверку и загрузку модулей. При иной схеме пакетов или отсутствии кандидата подготовку выполняет преподаватель; не устанавливайте произвольное ядро. Встроенный в ядро модуль может не иметь отдельного файла: это проверяется конфигурацией ядра и работой iptables. `Operation not permitted` — повод проверить права/политику Astra, а не отключать защиту. Окончательная проверка нужных расширений — успешный `iptables-restore --test` на шаге 4.

## 4. Необходимая теория

Служба создаёт сокет; firewall определяет, какие пакеты дойдут до него. Поэтому после фильтрации процесс может продолжать слушать порт, хотя Kali перестанет получать ответ. Доказательство сочетает `ss`, прикладной запрос, Nmap и счётчики правил.

В iptables таблица `filter` содержит встроенные цепочки `INPUT`, `OUTPUT`, `FORWARD`. Пакеты к локальной Astra проходят INPUT. Созданная нами пользовательская цепочка `PR8_N` сама по себе пакетов не получает. Её подключает единственное правило перехода из начала INPUT с условиями входного интерфейса и IPv4 назначения. Так учебный запрет не обходится более ранним общим разрешением INPUT. Другие интерфейсы, loopback и другие адреса назначения не попадают под этот переход. Политики встроенных цепочек и их прежние правила сохраняются.

В учебной цепочке разрешение выражено **RETURN**, а не ACCEPT: пакет возвращается к следующему штатному правилу INPUT и остаётся под действием исходной защиты. RETURN поэтому не гарантирует доставку. DROP окончательно отбрасывает пакет. Для выбранного TCP-порта пропускаются состояния NEW и ESTABLISHED, затем по варианту разрешается/отбрасывается UDP, допускается диагностический echo-request от Kali; всё остальное в области перехода отбрасывается. Это дополнительная узкая политика учебного IPv4-интерфейса, не универсальная конфигурация ОС.

Работа использует только IPv4. `ip6tables` и IPv6-политика **не изменяются**; результат нельзя распространять на IPv6. Правила не меняют OUTPUT, FORWARD, NAT и постоянную конфигурацию. ARP не фильтруется этой IPv4-цепочкой. Условие исходной линии — обе HTTP-службы и UDP отвечают с Kali при действующей штатной защите.

TCP `open` означает доступное соединение, `closed` — ответ об отсутствии принимающего сервиса, `filtered` — Nmap не смог установить доступность из-за фильтрации. UDP `open|filtered` не различает молчание службы и фильтрацию. Наш UDP-сервис отвечает только на точную строку `PR8?`, поэтому важен прикладной пробник. Счётчик показывает прохождение пакетов через правило, но без сопоставления времени и прикладного ответа не доказывает успех всей операции.

`iptables-restore --test --noflush` разбирает правила и проверяет создание набора без фиксации. `--noflush` обязателен: существующая таблица не сбрасывается. В файле объявлена только новая учебная цепочка, до начала которой не должно быть. Правила загружаются в неё отдельно, а переход из INPUT подключается последним. Откат сначала удаляет точный переход, затем очищает и удаляет исключительно свою цепочку. Он не восстанавливает глобальный снимок firewall поверх текущего состояния.

## 6. Ход выполнения

### Шаг 1. Параметры и исходные правила — 10 минут

Обе VM, Bash, обычный пользователь, `$HOME/pr8`. Замените N своим номером и параметры адресов паспортными; пример дан для N=1:

```bash
export N=1
export ASTRA_IP='10.50.1.10'
export KALI_IP='10.50.1.20'
export PORT_A=$((18000 + 10 * N))
export PORT_B=$((PORT_A + 1))
export PORT_UDP=$((PORT_A + 2))
export CHAIN="PR8_$N"
mkdir -p "$HOME/pr8/results"
cd "$HOME/pr8" || exit
printf 'N=%s Astra=%s Kali=%s A=%s B=%s UDP=%s\n' \
  "$N" "$ASTRA_IP" "$KALI_IP" "$PORT_A" "$PORT_B" "$PORT_UDP" | tee results/parameters.txt
```

Переменные действуют в текущем терминале: в каждом дополнительном терминале задавайте их снова. На Astra задайте LAB_IF настоящим именем внутреннего интерфейса, например `enp0s3` (без суффикса `@...`); не копируйте пример без проверки:

```bash
export LAB_IF='enp0s3'
ip -4 address show
ip -4 route get "$KALI_IP"
sudo iptables-save > results/iptables-before.txt
sudo ip6tables-save > results/ip6tables-before.txt
sudo iptables -t filter -S
systemctl is-active nftables ufw firewalld
systemctl list-timers --all 'pr8-rollback-*'
python3 tools/make_policy.py --variant "$N" --iface "$LAB_IF" \
  --astra "$ASTRA_IP" --kali "$KALI_IP" > policy.rules
```

Последняя команда должна завершиться кодом 0. При неверных параметрах исправьте их и повторите. Вывод is-active может иметь ненулевой код из-за отсутствующих служб: это не ошибка всего опыта. Старый ожидающий таймер собственного предыдущего опыта сначала разберите: выполните его откат и остановите именно этот таймер по шагу 7; он не должен удалить цепочку нового опыта. Чужие таймеры не трогайте. Если активный менеджер firewall может переписывать правила, согласуйте подготовленный образ, не отключайте менеджер самостоятельно. Не меняйте политику параллельно через Fly, UFW, firewalld, nft или другой терминал. На Kali проверьте `ip -4 route get "$ASTRA_IP"`. Оба маршрута должны использовать внутренние интерфейсы и адреса, без внешнего шлюза. Повторно убедитесь в отсутствии внешних маршрутов и наличии завершённых снимков.

### Шаг 2. Учебные службы и исходная линия — 15 минут

Сначала на Astra, обычный пользователь, проверьте, что порты свободны:

```bash
ss -lntup | tee results/sockets-initial.txt
```

При занятом порте не завершайте чужие процессы. Остановите только подтверждённый прежний собственный сервер; иначе используйте чистый учебный снимок с преподавателем. В отдельном терминале Astra вновь задайте N и ASTRA_IP, перейдите в `$HOME/pr8`, без sudo:

```bash
cd "$HOME/pr8" &&
python3 -u tools/lab_services.py --bind "$ASTRA_IP" --variant "$N" 2>&1 | tee results/services.log
```

Ожидание: сообщение о двух HTTP-портах и UDP; оставьте терминал открытым. В основном терминале Astra:

```bash
ss -lntup | tee results/sockets-before.txt
curl --noproxy '*' --connect-timeout 2 --max-time 3 "http://$ASTRA_IP:$PORT_A/"
curl --noproxy '*' --connect-timeout 2 --max-time 3 "http://$ASTRA_IP:$PORT_B/"
```

Ожидание: LISTEN обоих TCP, UDP-сокет и строки service=A, service=B. На Kali, `$HOME/pr8`, обычный пользователь (sudo только для UDP Nmap), выполните блок проверок:

```bash
PHASE=before
nmap -n -Pn -sT --reason --max-rate 10 --max-retries 1 --host-timeout 30s \
  -p "$PORT_A,$PORT_B" "$ASTRA_IP" -oA "results/tcp-$PHASE"
curl --noproxy '*' --connect-timeout 2 --max-time 3 "http://$ASTRA_IP:$PORT_A/" > "results/http-a-$PHASE.txt" 2>&1
printf 'curl_exit=%s\n' "$?" >> "results/http-a-$PHASE.txt"
curl --noproxy '*' --connect-timeout 2 --max-time 3 "http://$ASTRA_IP:$PORT_B/" > "results/http-b-$PHASE.txt" 2>&1
printf 'curl_exit=%s\n' "$?" >> "results/http-b-$PHASE.txt"
python3 tools/udp_probe.py "$ASTRA_IP" "$PORT_UDP" > "results/udp-app-$PHASE.txt" 2>&1
printf 'probe_exit=%s\n' "$?" >> "results/udp-app-$PHASE.txt"
sudo nmap -n -Pn -sU --reason --max-rate 10 --max-retries 1 --host-timeout 30s \
  -p "$PORT_UDP" "$ASTRA_IP" -oA "results/udp-$PHASE"
cat "results/http-a-$PHASE.txt" "results/http-b-$PHASE.txt" "results/udp-app-$PHASE.txt"
```

Сканируются только собственный IPv4 Astra и три порта. Запрещены подсети, сторонние узлы, -A, -sV, NSE, перебор и эксплуатация. Условие перехода: оба HTTP возвращают правильную страницу с кодом curl 0, пробник — `PR8 variant=N udp=ok` и код 0. Код пробника 2 означает тайм-аут, 3 — сетевую ошибку. UDP Nmap может показать open|filtered уже здесь. Если scan завершён по host-timeout, сохраните сообщение, не приписывайте непроверенным портам состояние. Для законченного scan допустимы и отдельные строки, и общая сводка одинаковых состояний.

Если исходных ответов нет, разберите адреса, маршруты, процессы и действующую защиту с преподавателем; новые правила пока не применяйте. Защиту не отключайте ради базовой линии.

### Шаг 3. Матрица и правила — 15 минут

На Astra, обычный пользователь, `$HOME/pr8`: составьте матрицу разрешений варианта и изучите `cat policy.rules`. Сверьте цепочку PR8_N, адреса и порты. Генератор только печатает текст и не меняет firewall. Файл содержит таблицу filter, объявление только своей цепочки и пять правил: INVALID DROP; разрешённый TCP RETURN; UDP RETURN/DROP; ICMP RETURN; остальное DROP.

Объясните, почему RETURN сохраняет действие штатного INPUT и почему не следует заменять его ACCEPT. Укажите предполагаемые результаты HTTP и UDP; отметьте IPv6 как отдельную неизменяемую область. В файле не должно быть объявления INPUT/OUTPUT/FORWARD, изменения их политик, NAT или глобального сброса.

### Шаг 4. Проверка и автоматический откат — 10 минут

На Astra, **из консоли гипервизора**, `$HOME/pr8`, административные действия через sudo. Выведите текущие цепочки и убедитесь, что имя PR8_N не занято:

```bash
sudo iptables -t filter -S
sudo iptables-restore --test --noflush < policy.rules
printf 'check_exit=%s\n' "$?"
```

Переходите дальше только при коде проверки 0 и отсутствии своей цепочки до опыта. Одного имени PR8_N недостаточно для признания найденной цепочки своей: при неизвестном происхождении остановитесь. Собственный прежний запуск удаляйте только способом шага 7. Опция --test не подтверждает прикладную связь.

Назначьте откат **до** применения. Сначала прочитайте [скрипт отката](tools/rollback.py): он удаляет точный переход с заданным интерфейсом/адресом и только PR8_N. Создайте его защищённую копию в /run; после этого таймер не зависит от изменяемого пользователем каталога tools:

```bash
export IPT_BIN="$(command -v iptables)"
export ROLLBACK_DIR="/run/pr8-$N"
export ROLLBACK="$ROLLBACK_DIR/rollback.py"
export ROLLBACK_UNIT="pr8-rollback-$N-$(date +%s)"
sudo install -d -o root -g root -m 700 "$ROLLBACK_DIR"
sudo install -o root -g root -m 700 tools/rollback.py "$ROLLBACK"
printf '%s\n' "$ROLLBACK_UNIT" | tee results/rollback-unit.txt
sudo systemd-run --unit="$ROLLBACK_UNIT" --on-active=45m \
  /usr/bin/python3 "$ROLLBACK" --iptables "$IPT_BIN" \
  --variant "$N" --iface "$LAB_IF" --astra "$ASTRA_IP"
systemctl list-timers --all "$ROLLBACK_UNIT.timer" | tee results/rollback-timer.txt
systemctl is-active "$ROLLBACK_UNIT.timer"
```

Ожидание: активный таймер с будущим временем запуска. Без рабочего таймера, защищённой копии и консоли не продолжайте. Срок 45 минут покрывает оставшиеся этапы, но следите за фактическим временем: при задержке сначала выполните откат, затем повторите опыт с новым таймером. Не применяйте правила одновременно со срабатыванием таймера.

Загрузите новую цепочку **с сохранением штатных правил**, затем подключите её единственным переходом:

```bash
sudo iptables-restore --noflush < policy.rules
```

Только если загрузка завершилась кодом 0:

```bash
sudo iptables -w 5 -t filter -I INPUT 1 -i "$LAB_IF" -d "$ASTRA_IP/32" -j "$CHAIN"
sudo iptables -t filter -S | tee results/filter-after-load.txt
sudo iptables -t filter -L "$CHAIN" -n -v -x --line-numbers | tee results/counters-loaded.txt
```

Проверьте код подключения: 0, один точный переход в начале INPUT, пять правил своей цепочки. При ошибке загрузки/подключения выполните ручной откат шага 7, разберите причину; повторно вставлять переход нельзя. Новая цепочка до подключения не влияет на пакеты. Штатные правила и политики не заменяются, файлы постоянной конфигурации не меняются. Не выполняйте iptables-restore без --noflush.

### Шаг 5. Повторная проверка — 15 минут

На Astra перед запросами сохраните счётчики:

```bash
sudo iptables -t filter -L "$CHAIN" -n -v -x --line-numbers | tee results/counters-before-tests.txt
```

На Kali **повторите весь блок запросов шага 2**, заменив только первую строку на `PHASE=after`. Адрес и три порта прежние. Ожидание: разрешённый HTTP отвечает, запрещённый не отвечает; UDP отвечает только в нечётном варианте. Для запрещённого TCP обычно filtered/тайм-аут. Ошибка сама по себе не считается доказательством запрета.

Сразу после запросов на Astra:

```bash
ss -lntup | tee results/sockets-after.txt
sudo iptables -t filter -L "$CHAIN" -n -v -x --line-numbers | tee results/counters-after-tests.txt
sudo iptables-save > results/iptables-after.txt
systemctl is-active "$ROLLBACK_UNIT.timer"
```

Оба TCP и UDP должны продолжать слушать. Сопоставьте рост allowed_http, variant_udp и deny_other_lab_input с конкретными запросами. Несколько пакетов на запрос нормальны; общий DROP может расти от фонового трафика, поэтому для неоднозначного результата сделайте отдельный запрос и замеры прямо до/после него. Нулевой счётчик при отказе требует проверки интерфейса, адреса, перехода и более ранней фильтрации. Если исчезла цепочка и восстановился доступ, проверьте журнал таймера: это может быть откат, а не ошибка политики.

### Шаг 6. Объяснение результата — 10 минут

Заполните таблицу 3 на основании файлов обеих VM. Объясните разницу между отказом службы и фильтрацией, ограниченность UDP scan, влияние штатного INPUT после RETURN и область IPv4. Не распространяйте вывод о трёх портах на всю защищённость ОС. Не подменяйте фактические наблюдения ожидаемыми.

### Шаг 7. Восстановление — 15 минут

На Astra, из консоли гипервизора, `$HOME/pr8`, sudo. Используйте сохранённые параметры того же опыта. Если терминал потерян, заново задайте N, LAB_IF, ASTRA_IP, IPT_BIN и ROLLBACK по шагам 1/4; имя таймера возьмите из results/rollback-unit.txt. Сначала запустите откат, и **только после его успеха** остановите ожидающий таймер:

```bash
sudo /usr/bin/python3 "$ROLLBACK" --iptables "$IPT_BIN" \
  --variant "$N" --iface "$LAB_IF" --astra "$ASTRA_IP"
```

При коде 0:

```bash
sudo systemctl stop "$ROLLBACK_UNIT.timer"
sudo iptables-save > results/iptables-restored.txt
sudo ip6tables-save > results/ip6tables-restored.txt
sudo iptables -t filter -S | tee results/filter-restored.txt
sudo journalctl -u "$ROLLBACK_UNIT.service" --no-pager > results/rollback-journal.txt
```

Ожидание: нет PR8_N и перехода к ней; прежние цепочки/порядок правил/политики сохранены; IPv6 не менялся. Если таймер уже сработал, повторный откат сообщает об отсутствии цепочки и безопасно завершается. Отсутствующий timer/service после удаления transient unit само по себе не означает сбой восстановления; сверяйте ruleset и связь. Не удаляйте другие цепочки и не обнуляйте их счётчики. `iptables-save` без -c сохраняет правила без динамических счётчиков, но содержит временные комментарии: сравнивайте содержательные строки, а не только байты файлов.

Пока службы работают, на Kali повторите блок шага 2 с `PHASE=restored`: оба HTTP и UDP должны отвечать как до фильтрации. Только затем нажмите Ctrl+C в терминале служб. На Astra сохраните `ss -lntup | tee results/sockets-stopped.txt`: три учебных сокета должны исчезнуть. Не используйте killall python3. При сбое отката сохраните доказательства вне VM, используйте консоль и восстановите снимок с преподавателем; не загружайте полный старый firewall поверх рабочего.

На каждой VM, `$HOME/pr8`, после завершения журналирования создайте контрольные суммы:

```bash
shopt -s nullglob
sha256sum results/* tools/*.py > SHA256SUMS.txt
if [ -f policy.rules ]; then sha256sum policy.rules >> SHA256SUMS.txt; fi
sha256sum -c SHA256SUMS.txt
```

На Kali policy.rules не генерируется и автоматически пропускается. Все перечисленные файлы должны существовать, проверка должна дать OK. Переносите результаты Astra и Kali в разные каталоги. После переноса запускайте проверку из каталога, содержащего results, tools и SHA256SUMS.txt. Удалять защищённую копию отката из /run во время опыта не требуется; после остановки таймера и проверки восстановления она исчезнет при перезагрузке VM.
