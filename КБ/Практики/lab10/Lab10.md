# Практическая работа № 10. Журналирование действий и корреляция событий

**Дисциплина:** Операционные системы. **Специальность:** 10.05.01 «Компьютерная безопасность», университет, 3-й курс. **Продолжительность:** 90 минут; подготовка пакетов и снимков выполняется заранее. **Варианты:** 27, номер соответствует номеру студента по списку в журнале.

Тема взята из раздела 4.2 РПД: настройка journald/auditd для входов, изменений конфигурации и доступа к контрольному файлу, безвредные события с Kali и временная шкала. Эта работа посвящена журналированию; одноимённый номер лекции 10 об архитектуре Astra не определяет тему практики.

**Вариант для предоставленного «Орла» 2.12.22:** сбор в journald, реальные уведомления файловой системы через inotify и события ограниченного учебного HTTP-сервиса. На данном ISO есть systemd 232 и inotify-tools 3.14, но нет пакета auditd. Установка auditd из другого дистрибутива не требуется и не допускается. Наличие libaudit1 или поддержки аудита в ядре не означает наличие auditd.

**Граница результата:** inotify сообщает о файловых событиях, но не устанавливает UID/PID процесса, совершившего обращение. Журнал показывает процесс-отправитель уведомления. Это не эквивалент auditd и не имитация его доказательств. Контрольный отказ HTTP 403 реализован приложением, а не PARSEC, DAC или firewall. Вход пользователя подтверждается настоящими сообщениями системы входа, не искусственной записью со словом LOGIN.

## 1. Цель и результаты

Цель — получить согласованную историю действий на двух учебных VM и объяснить, какие факты подтверждает каждый источник: настоящий журнал входа, сообщение приложения, уведомление inotify и клиентский запрос.

Задачи: проверить готовность ОС; направить stdout/stderr двух временных служб в journald; зарегистрировать один успешный вход; наблюдать чтение учебного файла и изменение учебной конфигурации; выполнить ограниченные запросы с Kali; сопоставить request_id, время, контекст и результат; оценить смещение часов; построить временную шкалу; восстановить файлы и остановить свои службы.

Результат — исходные JSON-журналы, ответы клиента, сравнительная таблица, CSV временной шкалы, расчёт неопределённости времени и подтверждение восстановления. Не делайте вывод о виновнике файловой операции только по совпадению временных отметок.

### 2.1. Проверка программ

На Astra, Bash, обычная учебная запись, домашний каталог:

```bash
cat /etc/os-release
uname -r
python3 --version
systemctl --version
for c in systemd-run systemctl journalctl systemd-cat inotifywait python3 ip ss ps date sha256sum sudo; do
    command -v "$c" || printf 'ОТСУТСТВУЕТ: %s\n' "$c"
done
dpkg-query -W systemd inotify-tools python3 iproute2 procps coreutils sudo
systemctl is-active systemd-journald.service
sudo journalctl -b -n 10 --no-pager
```

На Kali, Bash, обычная запись:

```bash
cat /etc/os-release
python3 --version
for c in python3 ip date sha256sum; do
    command -v "$c" || printf 'ОТСУТСТВУЕТ: %s\n' "$c"
done
```

Ожидание: команды найдены, journald активен и журнал читается. Обычному пользователю может потребоваться sudo для чтения системных событий; не расширяйте ради этого права всех пользователей. Если sudo отсутствует, установку выполняет преподаватель через консоль root. Сохраните выводы для отчёта.

### 2.2. Установка и временный NAT

Если пакеты уже доступны, установку пропустите. Иначе сохраните паспорт и снимки экрана текущих настроек сети. Выключите нужную VM, переключите **тот же единственный адаптер** на NAT. После запуска в штатном графическом менеджере проводного подключения выберите IPv4 «Автоматически (DHCP)» и автоматические DNS, примените и переподключитесь. Командами `ip -4 address show` и `ip -4 route` проверьте полученные адрес и маршрут. Пока NAT включён, учебные службы и запросы не запускаются. Bridged и второй адаптер не используются.

Проверьте источники `/etc/apt/sources.list` и файлы `.list`/`.sources` в `/etc/apt/sources.list.d`. На Astra нужен источник именно установленного выпуска/архитектуры «Орёл», на Kali — собственный официальный источник. Не смешивайте пакеты Debian, Kali, Common Edition и Special Edition.

На Astra, консоль обычного пользователя, установка через sudo:

```bash
sudo apt-get update
apt-cache policy inotify-tools python3 systemd iproute2 procps coreutils sudo
sudo apt-get -s install inotify-tools python3 systemd iproute2 procps coreutils sudo
sudo apt-get install inotify-tools python3 systemd iproute2 procps coreutils sudo
```

На Kali:

```bash
sudo apt-get update
apt-cache policy python3 iproute2 coreutils
sudo apt-get -s install python3 iproute2 coreutils
sudo apt-get install python3 iproute2 coreutils
```

Каждую следующую команду выполняйте после успеха предыдущей. Пробная установка не должна предлагать удалить защиту или сменить выпуск. При необходимости установите unzip отдельно. APT разрешает зависимости; полного обновления ОС не требуется. Проверку подписей и действующий firewall не отключайте.

Если старый сетевой репозиторий недоступен, подключите предоставленный ISO **того же выпуска** к виртуальному DVD Astra. Преподаватель регистрирует его командой `sudo apt-cdrom add`, затем устанавливает перечисленные пакеты через apt-get. inotify-tools и его библиотека имеются на проверенном носителе; успешную установку зависимостей подтвердите в VM. Для Kali используйте её репозиторий/подготовленный образ. Если источника не хватает, подготовьте совместимый локальный репозиторий или образ с преподавателем; не обходите проверку происхождения пакетов.

### 2.3. Поддержка ядра и возврат изоляции

В конфигурации штатного ядра 4.15.3-1-generic предоставленного образа inotify встроен (`CONFIG_INOTIFY_USER=y`). Это не модуль с именем inotify, поэтому команда `modprobe inotify` не нужна. Для иного работающего ядра, включая hardened, поддержку не следует выводить только из номера выпуска: она проверяется реальной готовностью наблюдателя на шаге 2. При ошибке поддержки ядра проверьте работающий выпуск и его штатный пакет ядра с преподавателем, не устанавливайте произвольное ядро.

После установки повторите проверки программ. Выключите VM, верните единственный адаптер на Internal Network `oslab-vNN`. После загрузки в графическом менеджере восстановите ручные адреса Astra `10.50.V.10/24` и Kali `10.50.V.20/24`, пустые шлюз/DNS и отключённое автоматическое получение DNS. Убедитесь, что не появился внешний маршрут IPv6; link-local удалять не требуется. На обеих VM выполните:

```bash
ip -4 address show
ip -4 route
ip -6 route
```

Ожидание: только учебный сегмент, нет default в обеих таблицах маршрутов, в гипервизоре только внутренний адаптер. Сохраните подтверждение. Затем штатно выключите обе VM, создайте `pre-lab10-VNN`, проверьте, что снимки появились и операция завершилась, запустите VM. Незавершённый live snapshot не является точкой восстановления.

Во время работы не меняйте PAM, SSH, штатный firewall, глобальные правила аудита, системное время и `/etc/systemd/journald.conf`. Не очищайте и не вращайте журналы. Перезагрузка до экспорта данных не допускается: журнал может находиться в оперативной памяти. Все изменения данных относятся только к `$HOME/pr10/labdata`; глобальный конфигурационный файл ОС не подменяется учебным.

## 3. Теория и пределы корреляции

journald собирает сообщения и добавляет служебные поля, например `_PID`, `_UID`, `_SYSTEMD_UNIT`, `_BOOT_ID` и временную отметку получения `__REALTIME_TIMESTAMP`. `MESSAGE` содержит текст отправителя. Поле с именем actor_pid внутри текста не становится автоматически доверенным полем ядра: его сообщает сама программа. Различайте метаданные отправителя и утверждения приложения о произошедшем действии.

В этой работе настройка источников journald выполняется на уровне **собственных transient-служб systemd**: им задаются обычный пользователь, StandardOutput=journal, StandardError=journal и отдельные SyslogIdentifier. Глобальная политика хранения не меняется. Запуск transient-службы требует sudo, но учебный Python-процесс исполняется с указанными обычными UID/GID. Временная служба не является установленным постоянным unit-файлом.

inotify наблюдает файловые события. OPEN означает открытие, ACCESS — доступ к данным, MODIFY — изменение, CLOSE_WRITE — закрытие после открытия для записи и само по себе не доказывает изменение байтов. Уведомления могут объединяться и поступать с задержкой; при переполнении очереди полноту наблюдения считать подтверждённой нельзя. `_PID` сообщения наблюдателя — PID наблюдателя, а не автора файловой операции. Без дополнительного источника inotify не устанавливает виновника и не даёт полноценного аудита всех системных вызовов.

В руководстве inotifywait 3.14 прямо указано предположение об отсутствии переполнения очереди. Поэтому отсутствие сообщения FS_LOSS **не доказывает**, что потерь не было. Малое число учебных запросов и проверка ожидаемых эпизодов ограничивают нагрузку, но не превращают этот наблюдатель в средство гарантированно полного аудита. Массовые файловые операции в опыте не выполняются.

Учебный HTTP-сервис сообщает request_id, адрес клиента, код HTTP, путь и контрольную сумму чтения. Параметр запроса связывает ответ и сообщение приложения. Самостоятельный наблюдатель подтверждает факт файловой активности, но не содержит request_id: связь с запросом в нём является гипотезой по времени, объекту и последовательности. Другие чтения — например, редактором или командой проверки — также создадут уведомления.

Часы Astra и Kali могут отличаться. Клиент сохраняет время отправки t₀ и получения t₁. Ответ `/ping` содержит время Astra s, взятое во время обработки. Если за этот интервал часы не изменялись, смещение «Astra минус Kali» оценивается интервалом **[s−t₁, s−t₀]**. Середина — оценка, половина RTT — неопределённость выбранной пробы. Скрипт выбирает пробу с минимальным RTT отдельно для каждого этапа. Это не синхронизация часов и не доказательство симметричности сети. При пересечении интервалов неопределённости порядок близких событий между VM нельзя объявлять строгим.

Журнал аутентификации — отдельный источник. Один успешный локальный вход создаёт реальные события login/PAM/systemd-logind, если они регистрируются текущей конфигурацией. Сообщение logind о создании сеанса подтверждает наблюдение менеджера сеансов, но не содержит автоматически способ проверки пароля или полный набор полей auditd. Отказ HTTP 403 в этой работе означает только решение нашего приложения.

## 5. Ход выполнения

### Шаг 1. Сессия, параметры и вход — 10 минут

Обе VM: Bash, обычная запись. Рабочий каталог `$HOME/pr10`; tools должны находиться внутри него. Если прежняя работа уже выполнялась, сначала сохраните весь прежний каталог под другим именем и подготовьте новый. В основном терминале Astra:

```bash
cd "$HOME/pr10" || exit
V=1
python3 tools/pr10.py init --work "$HOME/pr10" --variant "$V" > evidence-init.json
```

Замените 1 своим вариантом. init должен завершиться кодом 0, создать session.json, два файла labdata и исходную копию конфигурации в evidence. При уже существующей сессии он откажется её затирать. После успеха в том же терминале:

```bash
RUN_ID=$(python3 tools/pr10.py info --work "$HOME/pr10" --field run)
START=$(python3 tools/pr10.py info --work "$HOME/pr10" --field since)
PORT=$(python3 tools/pr10.py info --work "$HOME/pr10" --field port)
ASTRA_IP=$(python3 tools/pr10.py info --work "$HOME/pr10" --field astra)
KALI_IP=$(python3 tools/pr10.py info --work "$HOME/pr10" --field kali)
WATCH_UNIT="pr10-watch-$RUN_ID"
SERVER_UNIT="pr10-server-$RUN_ID"
TAG_WATCH="pr10-watch-$RUN_ID"
TAG_APP="pr10-app-$RUN_ID"
TAG_ADMIN="pr10-admin-$RUN_ID"
printf 'V=%s run=%s Astra=%s Kali=%s port=%s\n' "$V" "$RUN_ID" "$ASTRA_IP" "$KALI_IP" "$PORT" | tee evidence/parameters.txt
ip -4 address show | tee evidence/addresses.txt
ip -4 route | tee evidence/routes-v4.txt
ip -6 route | tee evidence/routes-v6.txt
ip -4 route get "$KALI_IP" | tee evidence/peer-route.txt
ss -lnt "sport = :$PORT" | tee evidence/port-initial.txt
```

Порт должен быть свободен, маршрут — через внутренний интерфейс. Если паспорт отличается, замените ASTRA_IP/KALI_IP подтверждёнными адресами перед запуском службы и зафиксируйте это; не меняйте сеть автоматически. Переменные действуют только в этом терминале; сохраняйте его открытым. В другом терминале их следует задать снова по session.json.

На Astra выполните **один успешный вход** обычной учебной записью через другую текстовую консоль (например, доступный терминал гипервизора с Ctrl+Alt+F3) или отдельный поддерживаемый сеанс GUI. Не выходите из основного рабочего сеанса и не используйте неудачные попытки входа. В новом сеансе сохраните подтверждение:

```bash
{
  id
  tty
  date -u
} > "$HOME/pr10/evidence/login-session.txt"
```

Зафиксируйте время успешного входа, затем завершите только новый сеанс командой exit/штатным выходом. Это безопаснее, чем создавать ошибку пароля после ПР6 с возможными ограничениями учётной записи.

В основном терминале Astra найдите реальные сообщения за окно работы:

```bash
sudo journalctl -b --since "$START" --no-pager -o short-iso _COMM=login + _COMM=sshd + _SYSTEMD_UNIT=systemd-logind.service
```

Выберите сообщение, относящееся к созданному сеансу, по пользователю, времени и типу события. Если сведений нет, с преподавателем уточните используемый источник PAM/GUI; не подделывайте запись и не выдавайте сообщение приложения за вход. Зафиксируйте фактический предел регистрации.

### Шаг 2. Настроить источники journald — 15 минут

На Astra, основной терминал `$HOME/pr10`, sudo только для управления systemd. Сначала запустите наблюдателя **с правами обычной записи**:

```bash
sudo systemd-run --unit="$WATCH_UNIT" --uid="$(id -un)" --gid="$(id -gn)" \
  --property=StandardOutput=journal --property=StandardError=journal \
  --property="SyslogIdentifier=$TAG_WATCH" \
  /usr/bin/python3 -u "$HOME/pr10/tools/pr10.py" watch --work "$HOME/pr10"
sudo journalctl -b -u "$WATCH_UNIT.service" -n 20 --no-pager
```

Условие продолжения — точная запись WATCH_READY и активная служба. WATCH_DIAGNOSTIC с сообщением «Setting up watches» не заменяет готовность. Если служба завершилась с ошибкой, выясните причину; файлы пока не меняйте.

Запустите сервис на проверенном внутреннем IPv4, разрешив только адрес своей Kali:

```bash
sudo systemd-run --unit="$SERVER_UNIT" --uid="$(id -un)" --gid="$(id -gn)" \
  --property=StandardOutput=journal --property=StandardError=journal \
  --property="SyslogIdentifier=$TAG_APP" \
  /usr/bin/python3 -u "$HOME/pr10/tools/pr10.py" serve --work "$HOME/pr10" \
  --bind "$ASTRA_IP" --peer "$KALI_IP"
sudo journalctl -b -u "$SERVER_UNIT.service" -n 20 --no-pager
systemctl show "$SERVER_UNIT.service" "$WATCH_UNIT.service" -p User -p Group -p MainPID -p StandardOutput -p StandardError
ss -lntp "sport = :$PORT" | tee evidence/port-running.txt
```

Ожидание: SERVER_READY, один учебный TCP LISTEN на адресе Astra, оба unit используют обычного пользователя и journal для вывода. Повышенный запуск Python от root не требуется. Сохраните вывод show в evidence/units.txt. Службы не включаются в автозагрузку и не создают постоянных unit-файлов.

### Шаг 3. Исходная серия с Kali — 15 минут

Kali, Bash, обычная запись, `$HOME/pr10`. Задайте V и ASTRA_IP по своему паспорту; RUN_ID скопируйте **точно** из evidence/parameters.txt Astra, включая 12 шестнадцатеричных символов. В примере строка RUN_ID — место замены:

```bash
cd "$HOME/pr10" || exit
mkdir -p evidence
V=1
ASTRA_IP='10.50.1.10'
RUN_ID='ЗАМЕНИТЬ_ТОЧНЫМ_RUN_ID_С_ASTRA'
ip -4 address show | tee evidence/addresses.txt
ip -4 route | tee evidence/routes-v4.txt
ip -6 route | tee evidence/routes-v6.txt
ip -4 route get "$ASTRA_IP" | tee evidence/target-route.txt
python3 tools/pr10_client.py --host "$ASTRA_IP" --variant "$V" --run "$RUN_ID" \
  --phase before --output evidence/client-before.jsonl
```

Клиент отвергает неверный номер/run, отключает HTTP-прокси и делает конечную серию: три clock-запроса, 1–3 чтения, status и denied. Единственная цель — собственная Astra, единственный TCP-порт — вариант. Нет сканирования подсети, эксплуатации, перебора или изменения файлов с Kali.

Ожидание: код клиента 0 и valid=True для всех строк. `/read` возвращает хеш искусственного текста, `/status` — mode=observe_NN, `/denied` — HTTP 403. Для denied код 403 является **ожидаемым прикладным ответом**. Ошибку сети, тайм-аут или отсутствие JSON нельзя выдавать за этот результат. Чужая версия RUN_ID не должна считаться подтверждённым ответом.

На Astra просмотрите новые сообщения:

```bash
sudo journalctl -b --since "$START" --no-pager -o short-iso -t "$TAG_APP" -t "$TAG_WATCH"
```

Найдите CONTROL_READ с request_id клиента, CONFIG_READ с исходным mode и FS_EVENT с путём контрольного файла/конфигурации. В JSON-просмотре `-o json` различайте actor_pid внутри MESSAGE и служебный `_PID`. Не требуйте точного количества FS_EVENT на запрос: события могут объединяться.

Если до исходной серии сервис недоступен из-за сохранённой политики ПР8 или иной защиты, не меняйте firewall в этой работе. Подготовьте с преподавателем предусмотренный исходный снимок, где учебная связь разрешена. Без успешной исходной линии корреляцию сетевого сценария не продолжайте.

### Шаг 4. Изменение конфигурации и повторная серия — 15 минут

Astra, основной терминал, обычный пользователь, `$HOME/pr10`. Измените только искусственный файл конфигурации и направьте сообщение действия в journal:

```bash
systemd-cat -t "$TAG_ADMIN" /usr/bin/python3 "$HOME/pr10/tools/pr10.py" configure \
  --work "$HOME/pr10" --state after
sudo journalctl -b --since "$START" --no-pager -o short-iso -t "$TAG_ADMIN" -t "$TAG_WATCH"
```

Ожидание: CONFIG_CHANGED с хешами до/после и файловые события MODIFY/CLOSE_WRITE для service_vNN.json. В рамках варианта правится существующий inode, без атомарной замены/переименования. Имя сервиса, профиль Astra и глобальная конфигурация journald не меняются.

На Kali с прежними V, ASTRA_IP, RUN_ID повторите:

```bash
python3 tools/pr10_client.py --host "$ASTRA_IP" --variant "$V" --run "$RUN_ID" \
  --phase after --output evidence/client-after.jsonl
```

Ожидание: status возвращает mode=check_NN; чтение контрольного файла и его хеш сохранены; прикладной отказ остаётся 403. На Astra подтверждаются CONFIG_READ с новым mode и новые request_id. Это позволяет связать изменение конфигурации с реально наблюдаемым поведением сервиса.

### Шаг 5. Восстановить данные и построить шкалу — 20 минут

Astra, основной терминал, обычная запись:

```bash
systemd-cat -t "$TAG_ADMIN" /usr/bin/python3 "$HOME/pr10/tools/pr10.py" configure \
  --work "$HOME/pr10" --state restore
python3 tools/pr10.py verify --work "$HOME/pr10" | tee evidence/files-restored.txt
```

Ожидание: CONFIG_RESTORED и restored=true. На Kali:

```bash
python3 tools/pr10_client.py --host "$ASTRA_IP" --variant "$V" --run "$RUN_ID" \
  --phase restored --output evidence/client-restored.jsonl
```

Ожидание: mode снова observe_NN и все контрольные ответы подтверждены. После этого на Astra сохраните данные **до перезагрузки**, не удаляя и не обнуляя журналы:

```bash
sudo journalctl -b --since "$START" --no-pager -o json \
  -t "$TAG_APP" -t "$TAG_WATCH" -t "$TAG_ADMIN" > evidence/events.jsonl
sudo journalctl -b --since "$START" --no-pager -o json \
  _COMM=login + _COMM=sshd + _SYSTEMD_UNIT=systemd-logind.service > evidence/auth.jsonl
```

Проверьте наличие последних событий, включая восстановление. Если сообщение ещё не дошло, сначала дождитесь его появления в просмотре и повторите экспорт; не считайте пустой файл готовым доказательством. Сохраните оригинальные JSONL отдельно от интерпретации. Из auth включайте в отчёт только относящийся к опыту сеанс; секреты и чужие сведения удаляются из публикуемой копии, а исходник хранится отдельно.

Через разрешённое средство гипервизора перенесите с Kali **три файла**, не целый каталог: client-before.jsonl, client-after.jsonl, client-restored.jsonl. Поместите их на Astra в evidence под именами `kali-before.jsonl`, `kali-after.jsonl`, `kali-restored.jsonl`. Одинаковые файлы двух VM не должны перезаписывать друг друга. Затем на Astra, без sudo:

```bash
python3 tools/pr10_timeline.py --journal evidence/events.jsonl --auth evidence/auth.jsonl \
  --client evidence/kali-before.jsonl --client evidence/kali-after.jsonl \
  --client evidence/kali-restored.jsonl --run "$RUN_ID" --output evidence/timeline.csv
```

Получаются timeline.csv и timeline.clock.json. Время клиента приводится к оценке часов Astra; исходные клиентские отметки остаются в JSONL. Шкала использует время получения journal и содержит отдельные источники. В ней поля sender_pid/sender_uid относятся к отправителю сообщения, **не к доказанному автору файловой операции**. Строки LOGIN_CONTEXT_REVIEW являются кандидатами для ручной проверки, не автоматическим заключением о способе входа.

Вручную сопоставьте минимум: успешный сеанс; исходное чтение; уведомление доступа к контрольному файлу; CONFIG_CHANGED и MODIFY; CONFIG_READ с новым mode; APPLICATION_DENIED; CONFIG_RESTORED. Покажите цепочку одного request_id между клиентом и сервисом и отдельно объясните, почему его нельзя искать внутри уведомления inotify. Не приписывайте каждому FS_EVENT однозначный запрос. Для близких межмашинных событий укажите неопределённость, а не придуманный строгий порядок.

### Шаг 6. Остановить свои службы и завершить доказательства — 15 минут

Astra, основной терминал, `$HOME/pr10`, sudo только для двух собственных unit:

```bash
sudo systemctl stop "$SERVER_UNIT.service" "$WATCH_UNIT.service"
systemctl is-active "$SERVER_UNIT.service" "$WATCH_UNIT.service"
ss -lnt "sport = :$PORT" | tee evidence/port-stopped.txt
python3 tools/pr10.py verify --work "$HOME/pr10" | tee evidence/final-state.txt
```

Ожидание: службы inactive либо уже выгружены как transient, учебного LISTEN нет, restored=true. Ненулевой код is-active в этом случае ожидаем; неизвестное имя unit не заменяет проверку порта и точного RUN_ID. Правила auditd, глобальная конфигурация journald, PAM, SSH, системное время и штатные службы не менялись. Не применяйте killall python3, не удаляйте весь /run и не очищайте journal. Сведения опыта сохраняются для отчёта.

На каждой VM, в `$HOME/pr10`, после завершения записи сформируйте суммы (в evidence должны находиться файлы, без вложенных каталогов):

```bash
sha256sum evidence/* tools/*.py > SHA256SUMS.txt
if [ -f session.json ]; then sha256sum session.json >> SHA256SUMS.txt; fi
sha256sum -c SHA256SUMS.txt
```

Ожидание: OK для каждого файла. После переноса проверяйте из корня соответствующего каталога pr10. Сохраните результаты двух VM отдельно. Если свои службы не остановились или восстановление не подтверждено, сохраните доказательства вне VM и используйте консоль/проверенный снимок с преподавателем. Снимок не заменяет объяснение причины неполного результата.

## 8. Диагностика и источники

Таблица 5 — Типовые затруднения

| Симптом | Проверить и сделать |
|---|---|
| auditd отсутствует | Он не требуется для этого варианта; libaudit1 не является демоном auditd |
| inotifywait отсутствует | Установить inotify-tools из совместимого репозитория/ISO; повторить проверку |
| Нет WATCH_READY | Состояние unit, ошибку inotifywait и права обычного пользователя; до готовности не выполнять опыт |
| Ошибка поддержки ядра | Работающее ядро и CONFIG_INOTIFY_USER; не пытаться modprobe inotify |
| journal пуст/недоступен | Службу, sudo для чтения, unit/identifier, окно времени; не ослаблять права всех пользователей |
| Клиент не подтверждает ответ | RUN_ID, V, порт, адрес, внутренний маршрут, состояние службы и штатную фильтрацию |
| HTTP 403 без нужного JSON | Возможно, другой сервис/неверный peer или RUN_ID; это не ожидаемый отрицательный тест |
| Нет ожидаемой записи о входе | Реально использованный GUI/TTY и источник PAM/logind; не подменять logger-сообщением |
| Уведомлений больше/меньше запросов | Объединение событий и сторонние чтения; не требовать соответствия один-к-одному |
| FS_LOSS | Наблюдение неполно; повторить ограниченный опыт в новой сессии и сохранить причину |
| Шкала уже существует | Сохранить прежнюю, выбрать новое имя; не терять исходные доказательства |
| Служба завершилась | Сохранить journal unit; сверить пути tools и версию Python, не запускать root вместо обычной записи |
